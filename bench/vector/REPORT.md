# 向量检索性能对比报告：kvstore VSEARCH vs faiss vs Milvus

> 原始数据 `results/vector_bench_2026-09-14.json`、`results/kvstore_scan_cost_2026-09-14.json`；
> 图在 `results/plots/`。测量脚本见本目录 `README.md`。
>
> **一句话结论**：kvstore 的 `VSEARCH` 暴力检索结果**完全正确**（与 faiss 精确检索逐条一致），
> 但比 faiss 的同口径精确检索慢 **4.8~11 倍**；在 10 万条以内，**暴力精确检索全面优于近似索引**
> （faiss HNSW 要达到可用召回反而更慢），也就是说项目「不做真 ANN，本地规模暴力足够」的
> 判断在本机实测下是成立的。

---

## 1. 测了什么

语义缓存那条读路径上的向量检索，三家实现在同数据、同查询、同 topk 下的表现：

| 系统 | 精确检索 | 近似检索 | 说明 |
| --- | --- | --- | --- |
| **kvstore** | `VSEARCH`（暴力余弦） | 无 | 自研 C 引擎，RESP/TCP 访问 |
| **faiss** | `IndexFlatIP` | `HNSW` / `IVF-Flat` | 进程内库调用，零拷贝 |
| **Milvus Lite** | `FLAT` | `AUTOINDEX` / `IVF_FLAT` | pip 内嵌单进程实现 |

生产口径（`ai-chat-service/dev.config.yaml`）：**dim=384、topk=30、命名空间 `semd:e5s:v1:`**。

## 2. 环境

- Intel Core Ultra 7 155H（**4 vCPU**）/ 7.7 GiB / KVM / Linux 6.1.176
- kvstore server 绑核 `2,3`（`taskset`，沿用 `tools/bench/bench_common.py` 口径），client 在核 0
- faiss-cpu 1.8.0、pymilvus 3.0.0、milvus-lite 2.5.1、numpy 1.24.4
- 数据：**聚类分布**合成向量（64 簇 + 噪声，单位化 ⇒ 内积即余弦），查询由库内点加小扰动生成（模拟"同一问题的改写"）。选聚类而非均匀随机，是因为真实 e5 嵌入同主题聚集、跨主题余弦饱和（配置里记 0.84~0.9）；均匀随机的近邻是退化的，会让 ANN 召回失真。
- ground truth 由 **faiss `IndexFlatIP` 独立计算**，与被测后端无关。

## 3. 结果

### 3.1 精确检索：延迟随规模

单线程逐条查询，dim=384、topk=30，单位 ms：

| N | kvstore VSEARCH | faiss FlatIP | 倍数 | Milvus FLAT |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.523 | 0.047 | **11.1×** | 0.952 |
| 10,000 | 4.620 | 0.654 | **7.1×** | 2.084 |
| 100,000 | 48.580 | 10.130 | **4.8×** | 1.373 ⚠ |

（p99 见原始 JSON；`latency_vs_n.png`）

三点值得说：

1. **VSEARCH 的召回在所有规模上都是 1.0000，且 `exact_match=true`** —— 与 faiss 精确检索的
   top-30 **集合完全相等**。这道校验顺便证明了 VSEARCH 的余弦与 top-k 选择没写错。
2. **kvstore 严格线性**：N 每涨 10 倍，p50 涨 8.9 / 10.5 倍。这是暴力扫描的必然结果
   （`kvs_vector.c` 遍历整张 `global_hash`，逐条算 384 维余弦）。
3. **kvstore 与 faiss 的差距随 N 缩小**（11.1× → 4.8×）：kvstore 每查询有固定开销
   （RESP 编解码 + TCP 往返 + 哈希表遍历），faiss 是进程内直接调用。N 小时固定开销占主导，
   N 大时两边都变成 O(N·dim) 的纯计算，差距收敛到"标量循环 vs SIMD"的比（faiss 用 BLAS）。

⚠ N=100,000 的 Milvus 数字**不可信**，见 §3.2 与 §5。

### 3.1b kvstore vs Milvus：约 2~5k 条处交叉

只取有效区间（N≤80,000，10 万那列见 §5.1 不可用），单线程 p50：

| N | kvstore VSEARCH | Milvus FLAT | Milvus IVF_FLAT | Milvus AUTOINDEX | faiss FlatIP |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | **0.523** | 0.952 (1.82×) | 0.910 (1.74×) | 1.024 (1.96×) | **0.047** |
| 10,000 | 4.620 | **2.084 (0.45×)** | 2.299 (0.50×) | 2.302 (0.50×) | **0.654** |

括号内是相对 kvstore 的倍数，**小于 1 就是比 kvstore 快**。

**这是 Milvus 对比里最要紧的一条：交叉点在 1 千到 1 万条之间。** 低于它，kvstore 的
VSEARCH 更快（1,000 条时快 1.8 倍）；一旦到 10,000 条，**连 Milvus Lite 都反过来比 kvstore
快 2.2 倍**。原因是两边的成本结构不同：

- kvstore 固定开销低（无 server 进程管理、无 RPC 序列化），但扫描是**标量循环**，随 N 线性上涨；
  10,000 条时要 4.6ms。
- Milvus Lite 固定开销高（约 0.85ms/查询的内嵌 RPC + 序列化），但扫描是**优化过的批量计算**；
  所以小 N 时被固定开销拖累，N 涨上来后反超。

**并发上 Milvus 优势更大**（N=10,000）：

| 系统 | build | QPS@1 | QPS@4 | p50@4 |
| --- | ---: | ---: | ---: | ---: |
| kvstore VSEARCH | 0.10s | 221 | **244** | **16.24ms** |
| Milvus FLAT | 2.86s | 469 | **561** | **6.02ms** |
| faiss FlatIP | 0.01s | 1,124 | 3,805 | 0.69ms |

4 个并发客户端下，Milvus 的 p50 是 kvstore 的 1/2.7，QPS 是 2.3 倍 —— 因为**kvstore 是单线程
reactor，VSEARCH 期间阻塞所有请求**（§3.3），而 Milvus 内嵌 server 是多线程的。

代价在另外两处：**Milvus 建库慢 28 倍**（2.86s vs 0.10s，N=10,000）且**内存口径不可比**
（Lite 是内嵌进程，RSS 增量没算它 mmap 的 `.db` 文件，见 §4.5）。

> 归纳：**kvstore VSEARCH 只在"数千条以内"这个区间有优势**。语义缓存的"本地规模"到底是多少，
> 直接决定该不该继续用暴力 VSEARCH —— 这是本项目最该先量清楚的一个数。

### 3.2 近似检索：召回—延迟权衡

近似索引的延迟必须和它自己的召回一起看，所以每个索引都扫了自己的召回旋钮
（HNSW 的 `efSearch`/`ef`、IVF 的 `nprobe`），共 21+21 个参数点（`recall_vs_latency.png`）。

**要把召回拉到 ≥0.95 需要多少延迟**（取首个达到该召回的参数点）：

| N | faiss HNSW | faiss IVF | kvstore VSEARCH（精确） | faiss FlatIP（精确） |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.057ms @0.980 | 达不到（最高 0.847） | **0.523ms @1.0000** | **0.047ms @1.0000** |
| 10,000 | 0.760ms @0.983 | 达不到（最高 0.895） | 4.620ms @1.0000 | **0.654ms @1.0000** |
| 100,000 | 达不到（最高 0.740 @5.0ms） | 达不到（最高 0.545 @2.3ms） | 48.58ms @1.0000 | **10.13ms @1.0000** |

**这就是本报告最重要的结论：在 10 万条以内，精确检索全面优于近似检索。**

- N=1,000 / 10,000：faiss `FlatIP` 精确检索 **0.047 / 0.654ms @ recall=1.0**，
  比 HNSW 达到 0.98 召回的 0.057 / 0.760ms **又快又准**。ANN 在这个规模毫无意义。
- N=100,000：HNSW 终于快过精确检索（5.0ms vs 10.1ms），但代价是 **recall 只有 0.74**；
  IVF 2.3ms 更是只有 0.545。想追平召回，HNSW 需要远大于 512 的 `efSearch`，代价会超过 10ms。
  **ANN 的优势要到更大规模才真正出现**，且必须接受明显的召回损失。

IVF 在小规模上是**错的工具**：它的 `nlist`（按 faiss 经验值 `4√N`）在 N=1,000 时有 126 个簇，
数据被切得比语义还碎，`nprobe=1` 时召回只有 0.05。这不是实现问题，是参数与规模不匹配。

### 3.3 并发吞吐：kvstore 单线程 reactor 是硬墙

| N | 系统 | QPS@1 | QPS@4 | p50@1 (ms) | p50@4 (ms) |
| ---: | --- | ---: | ---: | ---: | ---: |
| 10,000 | kvstore | 221 | **244** | 4.40 | **16.24** |
| 10,000 | faiss flat | 1,124 | 3,805 | 0.79 | 0.69 |
| 10,000 | milvus flat | 469 | 561 | 2.00 | 6.02 |
| 100,000 | kvstore | 20 | **20** | 49.28 | **193.64** |
| 100,000 | faiss flat | 99 | 307 | 10.04 | 12.65 |
| 100,000 | milvus flat | 706 | 1,043 | 1.37 | 3.11 |

kvstore 在 N=100,000 时：**4 个并发客户端，QPS 一点没涨（20 → 20），而 p50 准时涨了 4 倍
（49.3 → 193.6ms）**。这是"服务端完全串行"的教科书特征 —— `--net reactor` 单线程事件循环在
一次 VSEARCH 期间（49ms！）**阻塞所有其它客户端**。

生产含义：语义缓存的并发能力**不是**被 CPU 核数限制，而是被 `1 / VSEARCH延迟` 限制。
N=10,000 时单进程最多约 220 QPS 的缓存查询；N=100,000 时只有 20 QPS，且任何慢查询会
连累所有在线请求（尾延迟直接翻倍）。**这是 kvstore 侧最需要关注的瓶颈。**

faiss / Milvus 的并发数字**受 Python GIL 限制**（`base.py::measure_concurrency` 线程池的
每次调用都有 Python 层开销），不代表它们原生并发能力 —— 它们的真实并发要 C++ 侧多线程或
多进程才能测准，这里只作方向性参考。

### 3.4 建索引耗时与内存

N=100,000：

| 系统 | 空库→可查询 | 标称内存 |
| --- | ---: | ---: |
| kvstore（HSET 灌入） | **0.83s** | 192 MB |
| faiss FlatIP | 0.07s | 146 MB |
| faiss IVF | 27.1s | 200 MB |
| faiss HNSW | **263.5s（4.4 分钟）** | 204 MB |
| Milvus Lite（FLAT/IVF/AUTOINDEX） | 14.8s | ⚠ 46 MB |

- kvstore 灌数据最快（pipeline 批量 HSET），代价是没有任何索引结构可建。
- **faiss HNSW 建索引极慢**：10 万条要 4.4 分钟，且是单线程。若真要用 ANN，这个构建成本
  必须计入（增量场景下不可接受）。
- Milvus 的内存数字**不可直接用**：Lite 是内嵌进程，RSS 增量只反映了它自己新增的分配，
  没算它 mmap 的 `.db` 文件（实际落盘约 150MB+）。三个系统的内存口径并不严格可比。

### 3.5 kvstore 读路径：GET 那一跳几乎免费

生产的读路径是 `VSEARCH` → 取回命中候选的明文回答 `GET <问题原文>`（见 `semcache.go`
的 `vsearch` / `fetchAnswer`）。单独量出来：

| N | VSEARCH only | VSEARCH + GET | 增量 |
| ---: | ---: | ---: | ---: |
| 1,000 | 0.52ms | 0.55ms | +5.8% |
| 10,000 | 4.34ms | 4.35ms | +0.2% |
| 100,000 | 49.10ms | 49.12ms | +0.04% |

GET 走的是 array 引擎的 O(1) 查找，**相对动辄几十毫秒的 VSEARCH 完全可以忽略**。
优化重心应全部放在检索本身，不用管取回答这一跳。

### 3.6 VSEARCH 的隐性成本：扫的是整张表

`kvs_vector.c` 遍历**整个 `global_hash`**，对每个节点先 `memcmp` 前缀、命中才算余弦。
所以耗时 ∝ **整张 hash 表的节点数**，而不只是 `semd:e5s:v1:` 下的向量条数。
hash 引擎是通用 KV，语义缓存的向量和任何其它 HSET 数据共享同一张表，于是：

| 表内内容 | p50 | 相对 |
| --- | ---: | ---: |
| 10,000 条向量 | 4.33ms | 1.00× |
| +10,000 条无关键 | 4.61ms | 1.07× |
| +50,000 条无关键（累计 6 万） | 5.65ms | 1.31× |
| +100,000 条无关键（累计 16 万） | 8.58ms | **1.98×** |

增长是**次线性**的：无关键只付一次 `memcmp`（便宜），向量键要付 `memcmp` + 384 维余弦
（贵）—— 实测约 **16 条无关键 ≈ 1 条向量键**的成本。结论是：往 hash 引擎里塞别的业务数据
确实会拖慢语义缓存检索，但只要不是同量级的向量数据，影响有限（16 万条无关键才让延迟翻倍）。

## 4. 口径与公平性（重要）

这些数字**不能直接横向比较绝对值**，读的时候请带上以下几点：

1. **访问路径根本不同**。kvstore 是 `RESP 编码 → TCP → 服务端解析 → 哈希表遍历`；
   faiss 是**进程内函数调用**（零拷贝、零序列化）；Milvus Lite 是**内嵌 server + RPC**。
   所以 "kvstore 比 faiss 慢 7 倍" 里，有相当一部分是**网络与序列化**，不是检索算法本身慢。
   要拆开看，需要给 faiss 套一层服务端+网络，那是另一个实验。
2. **Milvus Lite ≠ Milvus**。它是 pip 内嵌的单进程实现，没有真实 Milvus 的分布式架构、
   独立 server 进程和网络跳数。**它的数字是真实 Milvus 部署的下界**，不能代表生产 Milvus。
3. **Python GIL**。faiss / Milvus 的并发 QPS 受限于测量进程的 GIL（§3.3），不是它们的能力上限。
4. **合成数据分布**。ANN 的召回对数据分布敏感；聚类分布下近邻结构"平坦"（余弦饱和），
   对图索引不友好，HNSW 的召回可能比在真实 e5 向量上更低。换成真实嵌入语料会改变 §3.2 的细节，
   但不改变"10 万以内精确检索足够好"的结论。
5. **内存口径不同**：kvstore 是 server 进程 RSS 增量，faiss 是测量进程 RSS 增量，
   Milvus Lite 连自己的 mmap 文件都没算进去。
6. **4 vCPU 单机、非独占**。绝对值无意义，只看相对关系与趋势。
7. **N=100,000 的 Milvus 数据是无效的**（见 §5）。

## 5. 发现的问题（两个，都影响结论可信度）

### 5.1 Milvus Lite 在约 9 万条以上会退化为近似检索 —— 连 FLAT 都不例外

N=100,000 时 Milvus 的 `FLAT`（应当是精确检索）与 ground truth 的 top-30 只重合 **8/30**。
逐项排查后确认**不是我方基准的 bug**：

- 行数**没丢**：`get_collection_stats` 返回 `row_count = 100000`；
- **无重复 id**（30 条全唯一）；
- 返回的距离**排序正确、且与该 id 的真实余弦完全一致**（排序没算错）；
- **自我检索仍能命中**（拿库内向量查询，5/5 以 dist≈1.0 找回自己）—— 说明它确实扫到了数据；
- 但**它就是跳过了真正的近邻**：真实第 2~7 名全没返回。

即：**它返回的是一个"排序正确但不完整"的 top-30** —— 这正是近似检索的特征，而不是数据缺失。

| N | 自我检索 | 与精确 top-30 重合 |
| ---: | ---: | ---: |
| 5,000 / 20,000 / 50,000 / 60,000 / 80,000 | 5/5 | **30/30** |
| 100,000 | 5/5 | **8/30** |

- 阈值在 **80,000 与 100,000 之间**，且与维度无关（dim=256、10 万条同样退化，排除了
  "128MiB 缓冲区"之类的字节数假设）；
- 更直接的证据：N=100,000 时 **`FLAT`、`IVF_FLAT`、`AUTOINDEX` 三种索引、以及所有
  `nprobe`/`ef` 取值，给出的 recall 和延迟完全相同**（recall 恒为 0.1503，p50 恒为 ~1.35ms）。
  搜索参数**完全不起作用**，说明 Lite 在这个规模上走的是一条固定的近似路径。

**因此 §3.1 表里 Milvus 在 N=100,000 的 1.373ms 看起来比 N=10,000 的 2.084ms 还快 —— 那是
因为它根本没搜全，不是性能好。**

> 影响：Milvus 的 100,000 那一列整列不可用。要拿可信的 10 万级 Milvus 数字，必须在真实
> Milvus Standalone（Docker）上重跑。由于本机 docker daemon 未启动、内存也紧张，本轮没有做。

### 5.2 `kvstore/kvstore/tools/test_vsearch.py` 已经跑不通了

这个冒烟测试用的是 **4 维**向量（`norm([1.0, 0.8, 0.6, 0.1])`），而 `kvs_vector.c` 的维度白名单
是 `{256, 384, 1024}`，所以服务端必然回 `ERR vsearch bad args`：

```text
$ python3 tools/test_vsearch.py
Exception: ERR vsearch bad args
```

仓库里的 C 单元测试 `make test_vsearch`（`tests/test_vsearch.c`）是**通过**的，所以坏的只是这个
Python 冒烟脚本 —— 它在维度白名单加上之后就没跟着更新。本报告未改动该文件（它在 kvstore
子模块里，属另一个仓库），建议改成 384 维 + `semd:e5s:v1:` 前缀。

## 6. 对语义缓存的建议

1. **先量清楚缓存到底有多少条 —— 这决定了要不要动。** 交叉点在 ~2~5k 条：
   - **数千条以内**：kvstore VSEARCH 是更优解（1,000 条时 0.52ms，比 Milvus Lite 快 1.8 倍），
     且召回精确。**什么都不用改。**
   - **万条以上**：连 Milvus Lite 都比 kvstore 快 2.2 倍、并发 p50 只有它的 1/2.7。
     此时"要不要换/要不要上 ANN"才成为一个真问题。

   注意即使到 10,000 条，**换 faiss HNSW 仍然是错的**（§3.2：精确检索 0.65ms 比 HNSW 达到
   同等召回的 0.76ms 更快），要换也该换成 faiss `FlatIP` 或 Milvus 这类"更快的精确检索"，
   而不是 ANN。项目"不做真 ANN"的决策在实测下**成立**。
2. **真瓶颈是串行，不是算法**。`VSEARCH` 期间整个单线程 reactor 停摆，4 个并发客户端
   就把 p50 从 49ms 推到 194ms（N=10 万）。**如果缓存 QPS 上不去，先解决这件事**，
   而不是先上 ANN：这条路（多线程/分片/把检索移出事件循环）的收益比换索引大得多。
3. **要提速的话，最省事的一步是给 `cosine()` 上 SIMD**。kvstore 现在是一维标量循环，
   faiss 用 BLAS。同样的精确检索，faiss 快 4.8~11 倍，其中相当一部分是这个差距。
   这比引入 ANN 依赖小得多，也不改变召回语义。
4. **要上 ANN，等 N 到十万级再说**，且必须接受召回损失（本机实测 10 万条时 HNSW 拿 0.74
   召回换 2 倍速度）。Milvus 在这个规模走 Lite 不可信，需要真实部署。
5. **别把其它业务数据混进向量所在的 hash 表**。16 万条无关键会让 VSEARCH 慢近一倍
   （§3.6）；分引擎或分前缀存放能避免这笔隐性开销。

## 7. 复现

```bash
cd bench/vector
python3 run_vector_bench.py            # 全矩阵，本机约 7.5 分钟
python3 kvstore_scan_cost.py           # §3.6 的全表扫描成本
python3 plot_vector_bench.py           # 出图
```

Milvus 的 `FLAT`/`IVF_FLAT`/`AUTOINDEX` 三者在 10 万条上表现完全相同这一异常现象，
