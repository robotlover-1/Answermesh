## 1. 贯穿全篇的选型哲学

这是一个**课程 9.1 的自研类 Redis KV 存储作为教学载体**的项目。很多"选型"的本质不是追求生产最优，而是**把不同技术实现出来做对比学习**。`tech-roadmap.md:121` 明确写道：

> 三模型并存不是为了生产冗余，而是为了对比学习。

这决定了理解本项目的正确姿势：每个技术都要问"它在这里承担什么学习/度量角色"。因此你会看到：

- 三套网络模型、五套存储引擎、三套内存后端**在一套代码里并存**；
- 技术迭代常以"先实现最朴素的版本 → 性能分析定位瓶颈 → 换更先进的技术 → 对比数据"为循环；
- 一些方案最终被标记 legacy（如 kprobe+RDMA），但保留在代码里作为历史参照。

## 2. 语言：为什么用 C

**为什么选 C**（`Makefile`：`CC=gcc -Wall -Wextra -O2`）：

1. **对标对象是 Redis，Redis 是 C 写的**——要"类 Redis"，RESP 协议、io_uring、epoll、RDMA、eBPF 这些底层操作天然是 C 的系统调用接口。
2. **多模型并存需要精确度量**：C 不引入运行时（GC/VM），能精确度量每层开销（60 字节内存 object、fdatasync 抖动、每命令 syscall 数这些微基准只有 C 能控制）。
3. **必须触碰内核**：eBPF（libbpf + clang 内嵌 BPF）、RDMA（librdmacm/libibverbs）、io_uring（liburing）——C 是能零开销表达这些的内核亲缘语言。

| 备选 | 为何不用 |
|---|---|
| **Go** | 只能当"客户端/微服务侧"（ai-chat 正是用 Go），当不了内核引擎；GC 污染微基准 |
| **C++** | 教学场景不需要 RAII/模板，C 是 Redis 母语；eBPF/RDMA 头文件是 C ABI |
| **Rust** | 内存安全代价是 unsafe 块 + 学习曲线，与"课程教学"目标冲突 |

**验证**：kvstore 全部源码是 C99 + Glibc，唯一链接 `-lm`（kvs_vector.c，提交 `13c05ec`）。

## 3. 网络模型迭代

### 3.1 演进时间线

| 阶段 | 提交/时间 | 说明 |
|---|---|---|
| 初始"network"（reactor/proactor/ntyco 三模型同帧出现） | `5a7fa95` 2024-05-18 | 网络层从一开始就是三模型并列（738 行） |
| io_uring 写入/持久化引入 | `8850c14` 2026-04-22 | io_uring 先从持久化用起 |

> **关键澄清**：项目**没有从 select/poll 在线演化到 epoll**。reactor 从第一笔 commit 起就是 `epoll_create/epoll_wait`（`tech-roadmap.md:152-158`）。select/poll 只作为对比/下线理论，主线始终是 epoll LT。

### 3.2 三种模型定位

| 模型 | 底层 | 定位 | 教学要点 |
|---|---|---|---|
| **Reactor** | epoll 水平触发 | 通用 I/O 密集，**默认** | 就绪通知 → 用户态读写 |
| **Proactor** | io_uring | 高并发 + 磁盘 I/O | SQE/CQE 提交-完成解耦，避免两次 syscall |
| **NtyCo** | 协程 hook 阻塞系统调用 | 海量连接、同步写法 | 同步编码体验 |

三者共享同一 `parse_resp_stream` 业务路径，只有 I/O 泵不同。配置 `net_backend` 默认 reactor（`kvstore.conf:18,40`、`kvstore.c:46`）。

### 3.3 Reactor 内部的微迭代（生产路径的进化）

epoll 在选中后持续被压榨（性能数据见文档 3）：

- `4c39b8b` accept4 + inbuf/out_ring 合并分配，降低建连开销。
- `46a8c9c` 事件循环末尾统一写（对齐 Redis beforeSleep），低 P 大幅提升。
- `6c5aac9` on_read 减少 EAGAIN 探测。
- `54273f0` 热路径消除多余 epoll_ctl syscall，ECHO +27%~+45%、HSET +15%~+36%。

## 4. 内存分配器迭代

### 4.1 演进

**libc（默认）→ jemalloc（LD_PRELOAD）→ custom（自研 slab+mmap）**。

| 后端 | 实现 | 角色 |
|---|---|---|
| libc | malloc/free | 开发基线 |
| jemalloc | LD_PRELOAD 装载 | 生产级、碎片少（对照） |
| custom | 自研 slab + mmap（`src/memory/kvs_mem.c`） | 可观测 + 释放归还彻底 |

### 4.2 为什么自研 custom（真正的选型理由）

`memory-backend-analysis.md` 的核心结论（数据见文档 3）：

1. **吞吐三者无区别**（±3%）——旧的单连接顺序测法 ~2300 QPS 是 RTT-bound 假象。
2. **custom 的价值是"释放后归还彻底 + 可观测碎片统计"**，不是写满密度。释放后 custom 靠 slab 页 munmap + 元数据 malloc_trim 几乎全还（残留 348KB，优于 jemalloc 的 2452KB）。
3. custom 的**弱点是内部碎片**——分配尺寸不贴合 class 就浪费。

### 4.3 custom 分配器自演进 4 阶段

（`optimization-history/custom-allocator.md`，按峰值 VmSize）：

| 阶段 | 改动 | 效果 |
|---|---|---|
| P1 | 空闲页回收（整页 munmap，阈值留 2 页） | 释放率 0→86% |
| P2 | 密集 slab class（8→17 级，2×→~1.25× 间距，参考 jemalloc/TCMalloc） | 97→89MB |
| P3 | 压缩 chunk header 24→16B | 89→81MB |
| P4 | free_stack 索引 16B→4B（per-page uint16 索引栈） | **80.7MB < libc 82.8MB，反超 libc** |
| P5 | 加 8/136 class + array 惰性分配 | 基线 VmSize 36.7→20.3MB |

### 4.4 为什么加 8/136 class 修 XSET 碎片

**问题**：XSET（跳表）节点做 3 次分配——node 32B、forward 数组、key、value。value=128 时分配 129B → 落 class 160（**浪费 24%**）；forward level0 8B → class 16（**浪费 50%**）。改前碎片率 14.1%、RSS 94MB。

**修改**（`069c5ae`）：`SMALL_CLASS_COUNT` 17→19，加 class 8 和 class 136。

**效果**：XSET 300k 碎片率 **14.1%→5.0%**、RSS 94→86MB（贴平 libc/jemalloc 87MB）。300k 个 value 全部精确落入 class 136，15 万 forward 落入 class 8。

> 2026-08-24 追加：custom_free 加 `malloc_trim` + 新增 `MEMORY_PURGE` 命令（`54181cb`）。

## 5. 持久化迭代

### 5.1 演进时间线

| 阶段 | 提交 | 动机 |
|---|---|---|
| **dump 二进制格式** | 早期 persist（`5fd43e2`/`239afe9`） | 全量落盘，`[klen][key][vlen][value]`，恢复优先 mmap |
| **AOF 命令日志** | `a1c6c4b` | 增量日志，RESP 命令格式，恢复=重放命令 |
| **io_uring 异步写** | `8850c14` | 解耦提交与完成，写盘不阻塞事件循环 |
| **group-commit 攒批窗口** | `454afb9` 引入 → 收敛 | 消除 fsync 率瓶颈：AOF always 100w **78.8k→118.7k**（窗口 2000µs） |
| **先回复 + 有界窗口** | `81092bc` | 回包不等 fsync，P=1 +79%；AOF 独立线程接管 io_uring（`d3b17ea`） |

### 5.2 关键决策

- **dump 为什么优先 mmap 恢复**：KVSD 是长度前缀布局（`uint32 klen + key + uint32 vlen + value`），天然适合从前到后 mmap 线性遍历，减少用户态拷贝；失败才回退 fread。
- **KVSD 统一**（`c458e04` 设计，`d5da881`/`fb80597` 落地）：早期全量同步用 RESP 快照、全量持久化用二进制 KVSD，两套生成/加载器。统一后**全量同步 + 全量持久化共用同一 KVSD 二进制格式**，唯一差异是走网络还是落盘。Slave load 不再过 parse_resp_stream 逐条执行，而是 mmap 后直接调 engine API。
- **appendfsync 收敛为 always/off**：早期有 everysec（`a1c6c4b`），后来 AOF 用 io_uring 异步写，everysec 的"每秒攒批"已被 **group-commit 攒批窗口**取代，配置收敛为 always/off（`e8a9453`）。
- **四种刷盘模式实验**（`aof-fsync-modes-analysis.md`）：异步批量/异步逐条/同步批量/同步逐条，方差根因是磁盘 fdatasync 延迟 285-643µs 抖动被异步 run-ahead 放大。最终默认为**异步批量 group commit + 先回复**（崩溃窗口稳态 ~1.3ms，加攒批窗口后 ~2.5ms）。
- **io_uring 的负结果**：实验证明"落盘才回包"模式下 io_uring 比直接 `pwrite+fdatasync` 还慢（36k vs 41k）——**io_uring 价值恰在"不等"（先回复 + 异步重叠）**。

## 6. 复制技术迭代

这是迭代最密集、提交最长的领域。

### 6.1 阶段时间线

| 阶段 | 提交/时间 | 驱动动机 |
|---|---|---|
| **TCP 全量复刻 Redis** | `8d497fe`/`5ffab40` | 最朴素 FULLRESYNC + 增量广播 |
| **eBPF sockmap 内核转发** | `8328438` 2026-04-24 | 内核态转发避免用户态拷贝 |
| **RDMA 全量同步（siw Soft-iWARP）** | `fb80597` 2026-06-11 | 全量数据加速 |
| **kprobe+RDMA 增量** | `53a4461` 前后 | 低延迟增量，但 hook 拖慢主路径 |
| **eBPF fentry + ebpf-proxy 独立进程** | `002c6a76`→`009b1c6` | 降到 ~5% 开销 + 可跨机 |
| **当前：RDMA 全量 + eBPF+tcp 增量双通道** | 定型 | 稳健 + 易用 + 性能平衡 |

**当前默认**（`kvstore.conf:52/59`）：`repl_fullsync_transport=rdma`、`repl_realtime_transport=ebpf+tcp`，RDMA 设备 `siw0`。

### 6.2 为什么换：性能 vs 易用 vs 健壮性

- **TCP→RDMA 全量**：性能。跨机 MTU 9000 提速 5.7×（0.37→2.09 Gbps，见文档 3）。
- **kprobe+RDMA→ebpf+tcp**：**健壮性 + 易用性**。kprobe 每 `tcp_recvmsg` 触发两次 BPF 拖慢主路径，且要维护 RDMA WRITE 增量 QP、MR 交换、偏移对齐，跨机调试极痛苦。ebpf+tcp 用 TCP 做增量（天然可靠），只把"捕获"阶段 BPF 化，复杂度骤降。

### 6.3 为什么用 Soft-iWARP（siw0）而不是真 RDMA 网卡

**KVM 教学环境约束**：

1. **无真网卡**：环境是 KVM 虚拟机，宿主机没有 Mellanox 等真 RDMA HCA，只能软件模拟。
2. **siw = Software iWARP**：`rdma link add siw0 type siw netdev ens33`（README:49-52），用普通以太网卡在驱动层模拟 RDMA，`librdmacm/libibverbs` 应用层代码与真卡完全一致。
3. **验证用途**：README 明说"RDMA 使用 Soft-iWARP(siw0) 验证"，目的是验证 RDMA 语义（WRITE/RC QP），不是追求真卡带宽。

**为什么 rxe0+siw0 双设备破坏跨机 RDMA**（README:49-50、memory `kvstore-128-rxe0-zombie`）：rxe0（Soft-RoCE）和 siw0（Soft-iWARP）**同时绑定同一 ens33** 会造成路由/设备选择冲突，`rdma_accept` 失败、跨机 RDMA 回退 TCP。根因是多个 RDMA device 挂在同一 netdev 上，内核/rdma_cm 无法唯一解析目标 `{netdev, gid}`。修复 = `setup-rdma.sh` 只建 siw0、删除残留 rxe0。

### 6.4 RDMA 内部迭代（健壮性主线）

- **两遍式→单边 WRITE**（`0ab16f4`）：IBV_WR_SEND → IBV_WR_RDMA_WRITE，去掉 SEND 预热。
- **Pipeline**：单 send buffer 同步等待 → 4 slot 环形 + 后台 CQ 轮询线程（`tech-roadmap.md:1036-1126`），消除 100-500µs/次同步等待，CPU ↓80%。
- **健壮性修复**：EAGAIN drain 重试（`6dca33a`）、SEND 预热 rxe QP（`e31013e`）、FULLRESYNC 头走 TCP 控制面（`3dde192`）、memlock setrlimit（`b32db3a`/`0ad793f`）、CQ 轮询线程竞态段错误（`5304e2d`）。

## 7. eBPF 转发迭代

**核心演进**：sockmap（sk_msg）→ kprobe → **fentry/fexit**，且**从内核态转发改为用户态 ebpf-proxy 独立进程**。

### 7.1 六次迭代（`ebpf-forwarding-optimization-journey.md`）

| 迭代 | 方案 | 结果 |
|---|---|---|
| 0 | kprobe/kretprobe on `tcp_recvmsg` + ringbuf | 落后 8-39% |
| 1 | fentry/fexit trampoline | 落后 11-45% |
| 2 | sockmap sk_msg `bpf_msg_send_data` | **不可行**：helper 在所有内核都不存在，只能 redirect 不能 tee |
| 3 | 纯用户态 async ring buffer + 线程 | 5/7 超 sync |
| 4 | TC `bpf_clone_redirect` + VXLAN | 与 sync 持平 |
| 5 | **ebpf-proxy 独立进程（最终）** | ~5% |
| 6 | fentry+fexit + batch writev + libbpf 1.5.0 | 小负载持平、4KB +37% |

### 7.2 为什么从内核态转发改为用户态 ebpf-proxy 独立进程

三个决定性原因（journey 文档 305-309）：

1. **任何挂主 I/O 路径的 BPF hook 都拖慢 echo**：kprobe entry+return 各 ~3-5µs，fentry 仍在每次全局 `tcp_recvmsg` 上执行（含 SSH 等系统流量）。
2. **把 ringbuf 消费者放到独立进程**：master 进程只 echo、不加载 BPF，BPF 开销虽仍在 master `read()` 路径，但 ringbuf 消费者移到别处，避免阻塞主循环。
3. **PID 隔离防反馈循环**：slave 必须在独立进程（不同 PID），否则 BPF 会误捕获 slave 的 `read()`，数据无限放大。

### 7.3 ringbuf 与批量 writev

- BPF 侧 `bpf_ringbuf_output` 到 4MB ringbuf，用户态 `ring_buffer__poll` 消费，解耦 BPF 上下文与用户态消费速率。
- 生产转发线程化（2026-08，跨机 QPS 主线）：
  - `79abcc4`/`83b06d29`：转发拆独立线程（入队+转发）。
  - `1e921b1`：转发环形缓冲 + **入队去每命令 cond_signal**（sync 跨机 56k→80k，+84%）。
  - `b8aa350`：转发线程**批量 writev**（BATCH_MAX=64），ebpf 28k→48k（+72%）。

## 8. 基准测试工具（harness）迭代

harness = `tests/perf/test_ebpf_hset_qps.c` 等，价值是把生产转发路径抽出来做可复测的 QPS 实验。演进主线是**为消除测量假象、对齐生产**：

| 阶段 | 提交 | 变化 |
|---|---|---|
| 早期 | `02c6a76` 前后 | 进程内内联转发 + 全局锁 |
| 单线程 epoll reactor 对齐生产 | `9894228` | 用同一声明让 none/sync/ebpf 三模式 master 完全一致 |
| --keyrange 固定键范围 | `6744dc2` | 消除随机键 RNG 碰撞导致"只写 ~2 万键"假象 |
| 无锁 SPSC sync | `6744dc2`/`1e921b1` | 转发队列改固定环形缓冲 + 单消费者 FIFO |
| 诊断开关 + 方法论修正 | `ce97f95` | 修正 eBPF 对比假象；统一 QPS 口径（墙钟时间） |

**方法论踩坑**（memory `kvstore-benchmark-methodology-gotchas`）：redis-benchmark 默认连 6379、--pipe 与 -c 50 差异、appendfsync always vs everysec 是关键差异；**单线程客户端测超快服务器给的是客户端上限**，验证瓶颈要加客户端线程数而非 -c。统一标准最终用 `memtier -t 2 -c 50`（详见文档 3）。

## 9. ai-chat 技术栈选型

ai-chat 是"零声教学 AI 助手"微服务版，2026-08-16 合并进 kvstore 仓库（`3bf24df` 单一仓库）。定位见 `统一项目说明.md`：**"用自己写的 Redis（kvstore）给一个 AI 聊天系统当短期记忆"**。

### 9.1 技术栈

| 组件 | 选型 | 理由/证据 |
|---|---|---|
| 网关 | ai-chat-backend，Go + Gin（:7080） | 托管前端 + 登录/验证码 + 入口限流 + 鉴权 + 计费 |
| 核心服务 | ai-chat-service，Go + 自研 C zrpc v2（:50055，流式） | 对话编排 |
| 过滤 | keywords-filter，Go + 自研 C zrpc v2（:50053/:50054），AC 自动机 | 敏感词/关键词 |
| 前端 | Vue3（chatgpt-web 系）pnpm build | 浏览器逐行解析 NDJSON |
| 计费 | MySQL users(phone,quota) + chat_records | docs/sql/create_db.sql |
| token/嵌入 | Python tokenizer（:3002，jieba /embed + /rerank） | 见文档 4 |
| 大模型 | openai-api-proxy（:8084）→ DeepSeek API（deepseek-v4-flash） | go-openai |
| 短期记忆 | **自研 kvstore（:5160）** 替代原 Redis | RESP + AUTH + SETEX |
| 监控 | Prometheus + Grafana | monitoring/ |

> 更新(2026-09-04)：核心/过滤服务间的 gRPC 已迁移到自研 C zrpc v2（gRPC 传输已删），把课程「造轮子」再推一层——自研 RPC 替换 gRPC。实现步骤与用法见 `third_party/zrpc/README.md` 与 `zrpc-go/`。

### 9.2 为什么 Go + gRPC 微服务

- **与 kvstore 的 C 形成互补分工**：Go 做 HTTP/gRPC 高速并发网关与编排，C 做持久化内核。Go 的 Gin、gRPC 生态是微服务标配。
- **架构借用论**：ai-chat 源自开源 chatgpt-web 前后端 + 零声微服务脚手架教程，Go+gRPC 是教程既定方案；本项目把**存储层**换成自研 kvstore，形成"我写的 Redis 服务我的 AI 聊天系统"的闭环。

### 9.3 为什么语义缓存用自研 kvstore 而不是腾讯 vectorDB

**决策演进的铁证**：`6abc8bf`（语义缓存 CacheQuery/CacheWrite **替换腾讯 vectorDB 路径**）、`e82d7f5`（**删腾讯 vectorDB 死代码**）。

语义缓存设计文档原话：

> ai-chat 原有知识库走腾讯云向量库（tcvectordb SDK），云资源不可达，路径失效。本设计把知识库做成完全本地可达的语义问答缓存（复刻 InazumaPlasma 架构，但全部落在自研组件上）。

动机拆解：
1. **云资源不可达**（直接原因）：tcvectordb 是腾讯云托管服务，教学环境没有外网/云资源。
2. **落地在自研组件**（架构原因）：kvstore 加 `VSEARCH` 命令，tokenizer 加 jieba 轻量嵌入（256 维，零大依赖），ai-chat-service 加 CacheQuery/CacheWrite。**复用 SET 存储（AOF/dump 自带持久化），不新增 VADD/VDEL、不做真 ANN**（本地规模暴力足够）。
3. **本机内存约束**：3Gi 内存排除 torch/transformer，jieba 纯 Python 可装。
4. **防误命中**：jieba 稀疏嵌入下无关问题可能分数反超，须"分数达标 + 共享实质关键词 rerank 校验"双条件（`0200236` 加共享关键词门禁，`7bb4977` /embed + /rerank）。

### 9.4 openai-api-proxy 的角色

- **钥匙保管箱**：真 DeepSeek key 只在 proxy 配置，service 用假 token。
- **供应商适配层**：换模型/厂商只改 proxy 的 base_url+api_keys，编排服务零改动。
- **扩展挂载点**：重试/超时/多 key 轮换/成本统计不用动 service。
- **开源 AI 门禁兜底**：backend 限流被绕过，proxy 在"花钱的 API 调用"这层再兜一道。

## 10. 部署迭代

### Docker Swarm → 本地一键脚本

两个部署面：
1. **生产编排（保留）**：`ai-chat-stack/`（compose.yaml）走 **Docker Swarm**，镜像来自私有仓库 `192.168.239.161:5000/2404/<svc>:1.0.0`，滚动更新 + 健康检查 + 配置注入。
2. **本地开发（新增）**：`start.sh/stop.sh/lib.sh`（2026-08-15 simplify-startup）一键启停 8 个服务（kvstore → tokenizer → sensitive → keywords → mock → proxy → ai-chat-service → ai-chat-backend）。

**为什么加 start.sh**：原手工分步（前端 pnpm + 后端 go build + 手动 nohup 起 8 个服务）易错。start.sh 做了：
- 缺失二进制/源文件更新/--rebuild 时自动补编译；
- 前端 dist 与 backend/www 缺一即重建；
- 幂等（端口已监听则跳过）；
- 端口轮询等待 30s 判定成功。

**监控**：ai-chat-service 暴露 Prometheus 指标（:8080），Grafana :3000 展示服务健康与 QPS，是 ai-chat 从"能跑"到"可观察"的关键。

## 11. 选型决策表汇总

| 维度 | 选择 | 备选 | 为什么 |
|---|---|---|---|
| 语言 | C | Go/C++/Rust | Redis 母语、零运行时精确度量、内核亲缘 |
| 网络模型 | Reactor(epoll) 默认 | io_uring/NtyCo | 通用 I/O 密集；三者并存对比学习 |
| 内存后端 | libc 默认 | jemalloc/custom | custom=归还彻底+可观测；默认 libc 求稳 |
| 持久化 | AOF(io_uring group commit)+dump | — | 先回复+攒批消除 fsync 瓶颈 |
| 全量同步 | RDMA WRITE | TCP sendfile 回退 | 性能，Soft-iWARP 验证 RDMA 语义 |
| 增量同步 | eBPF+tcp | kprobe-rdma(legacy)/tcp | 捕获 BPF 化 + 传输可靠 + 易调试 |
| 语义缓存 | kvstore VSEARCH | 腾讯 vectorDB(弃) | 云资源不可达 + 全自研闭环 |
| 微服务 | Go + 自研 C zrpc v2 + cgo | — | 与 C 内核互补；课程造轮子（自研 RPC 替换 gRPC） |
| 部署 | 本地 start.sh | Docker Swarm(生产) | 教学环境一键启停 |
