## 1. 测试体系总览

### 1.1 组织方式：Makefile 目标 + 独立脚本两层

**① Makefile 目标层**（`kvstore/Makefile` + README「全部测试目标」表）

- 统一入口：`make check`（基础 resp+ttl+persist+doc）、`make check-all`（全部，自动探测 RDMA/eBPF 并跳过不可用项）、`make check-all-quick`（跳过 RDMA/eBPF/复制/demo）。
- **关键机制**：多数 check 目标经 `tools/tests/run_with_kvstore.py` 包装——自动拉起 kvstore、抽 args 里的 `{HOST} {PORT}` 占位符、跑完清理进程。测试程序不关心 server 生命周期。
- 测试产物统一落到 `artifacts/<类别>/`，如 `artifacts/persist/uring-bench/`、`artifacts/repl/rdma-stress/`。

**② 独立脚本层**（`tools/tests/`、`tools/repl/`、`tools/persist/`、`tools/bench/`）：`test_master_slave_multi_engine_nc.sh`（多引擎主从）、`run_save_bgsave_perf_test.sh`（SAVE/BGSAVE 性能）、`run_aof_bench.py`（AOF 并发）、`run_pipeline_bench.py`（Pipeline）、`run_save_bench.py`（SAVE）、`mem_pool_bench.py`（内存）等。

**③ 自研 C harness**（`tests/perf/`）：`test_ebpf_hset_qps.c`（主从转发 QPS）、`test_rdma_throughput.c`（RDMA 吞吐）、`test_sendfile_throughput.c`（sendfile 吞吐）、`test_ebpf_proxy_qps.c`（ebpf-proxy 转发 QPS）。

## 2. 基准测试方法论

### 2.1 用 redis-benchmark 还是自研 harness？

分三类：

1. **redis-benchmark**：早期 AOF/SAVE/Pipeline 数据（`tools/bench/run_persist_bench.sh`）。
2. **memtier_benchmark（2026-08-25 统一标准）**：`memtier_benchmark -t 2 -c 50 --pipeline N -d 16`（单进程 2 线程 × 50 连接 = 100 连接），**取代单线程 redis-benchmark**，规避客户端测量上限坑。
3. **自研 C harness**（`tests/perf/`）：`test_ebpf_hset_qps.c`、`test_rdma_throughput.c`、`test_sendfile_throughput.c`、内存后端 `tools/bench/bench_mem_backend.py`。

### 2.2 客户端测量上限坑（方法论最核心教训）

专门成文 `kvstore/docs/data_analysis/benchmark-methodology-qa.md`：

- **`-c` 与客户端线程数是不同维度**：单线程 redis-benchmark 测超快服务器时，报告的是**客户端上限而非服务端能力**。判断瓶颈要**加客户端线程/进程数**（分核、均分连接数），**不是加 `-c` 连接数**。

  实证：kvstore ECHO，并发两个客户端进程（核 0/1 各 `-c 25`）各 P 均 **+36-40%**（P=8: 902k→1266k，P=160: 7843k→10662k）。而 HSET 双客户端无提升（±4%），确认是服务端瓶颈。**这解释了为何最终改用 memtier 双线程才测出 kv 全面超 redis 的正确曲线。**
- **`--pipe` vs `-c 50` 差异**：appendfsync always vs everysec 是另一个关键差异维度（见 §4）。
- **毫秒计时量化假相等**：`RPS = n/elapsed_ms`，两服务器落同一 ms 桶会报告逐位相同 QPS，必须回原始轮次核对。
- **ECHO P=20 比值谷底是测量巧合**：P=20 处单客户端上限 ≈ redis 服务端速率，判定证据是比值随 P 非单调。
- **ECHO 基准 bug 修正**（`2c40a27`）：redis-benchmark 对自定义命令仅在 `-r` 存在时替换 `__rand_int__`。原 `echo`（argc=1）命中 wrong-argc 错误路径，测的是"错误拒绝吞吐"假象；改 `echo __rand_int__` 后 ECHO 反转（kv P160 ~7.5M vs redis ~4.3M，+172%）。
- **绑定核与否**：AOF 波动 ±12-20% vs ±2-7%，服务端+客户端都须 taskset 隔离核。
- **单客户端 CPU-bound 时「服务端越慢、客户端测得越高」的反向污染**（2026-08-12 确证，见 §7.4）：redis-benchmark 单进程 ~98-99% CPU 完全 CPU-bound 时，P=1 测得的是**客户端自己的 CPU 吞吐**（`QPS = CPU 预算 ÷ 每请求 CPU`），且每请求 CPU 被**服务端应答时序反向左右**——服务端越快（none）回复越分散、客户端每请求 syscall 越多（recvfrom/epoll_ctl 不合并）→ 测得越低；服务端越慢（sync/ebpf 转发 +~234ns）回复越集中、客户端收包越合并、省 syscall → **测得反而越高**。因果确证：给 none 服务端加 500/1000ns 纯延迟，客户端 QPS 从 ~100k **升到** ~105k/~109k。**判断客户端是否成为瓶颈**：加客户端进程数（分核）或高 P 让服务端饱和；双客户端后真实排序浮现（none 201k > sync 185k ≈ ebpf 183k）。

### 2.3 踩坑清单


| 坑                 | 现象                              | 结论                             |
| ------------------ | --------------------------------- | -------------------------------- |
| 客户端单线程上限   | kv ECHO 全 P 顶到客户端吞吐       | 双客户端验证才是真值             |
| ms 精度假相等      | 两服务器报告逐位相同 QPS          | 回原始轮次核对                   |
| ECHO 谷底          | P=20 ratio~101%                   | 测量巧合，非服务端交叉           |
| 内存后端单连接假象 | 单连接 ~2300 QPS                  | RTT-bound，需多连接/P 反推       |
| 空表测"100w"是虚的 | 多连接随机键碰撞只写 ~2 万键      | 须先 populate 真实数据量再测稳态 |
| 稀疏流量崩溃窗口   | 攒批窗口下孤立写延迟膨胀到 ~100ms | 验证崩溃窗口须测稀疏单条写       |
| 单客户端反向污染   | CPU-bound 下服务端越慢客户端测得越高（sync/ebpf>none） | 双客户端分核或高 P 才显真实排序   |
| 全挤单核共享       | 客户端+master+转发同核 → sync/ebpf ≈ none 的 50%       | 转发/客户端 pin 独立核            |

## 3. 性能测试：内存后端与 custom 分配器

> README 位置：「性能基准 → 内存后端」。测试脚本：`tools/bench/mem_pool_bench.py`（内存）、`redis-benchmark`（吞吐）。

### 3.1 测试方法

- **吞吐**：`redis-benchmark -c 50 -P N HSET key:__rand_int__ value`，三后端各自独立实例，taskset 隔离核 2/3，3 轮中位数（早期多连接口径）。
- **内存占用/归还**：写入 100w 条 HSET → 释放 100w 条 HDEL，在 1%/10%/50%/80%/100% 进度点采样 `/proc/<pid>/status` 的 VmSize/VmRSS；**2026-08-24 统一口径**：50 并发连接（与随机 key 场景一致）、free100 后显式 `MEMORY_PURGE` 再采样。

### 3.2 起点：初测数据有多差

- **吞吐上是"测不出来"**：早期 `bench_mem_backend.py` 单连接顺序发命令，三后端都只有 **~2300 QPS**——这是 RTT-bound 的假象，单连接顺序等待响应，测的是网络往返不是分配器能力。**这条弯路一度让"custom 有吞吐优势"的说法无法成立**。
- **custom 分配器初始实现**（8 级 class `{32,64,...,1024}` 间距 2×，24B chunk header，空闲页从不 munmap）：写入 100w 后**删除全部数据，95MB 物理内存纹丝不动（释放率 0%）**；峰值 VmSize **96,592 KB，比 libc（82,764 KB）高 32%**，bytes/条目 98.9 vs libc 84.7。当时 custom 是"最省内存"的宣传，实际是最差的。

### 3.3 优化历程（custom 分配器 5 个 Phase）

> 出处：`kvstore/docs/optimization-history/custom-allocator.md`（按 100w HSET 峰值 VmSize 演进）。

**Phase 1：空闲页回收（释放率 0% → 86%）**

- **动机**：`custom_free` 只把 chunk 放回 `free_list`，slab 页（mmap）从不归还内核，删数据内存不还。
- **改动**：per-page 追踪 `chunks_in_use`，整页空闲（`chunks_in_use == 0`）时 `munmap` 归还 OS；保留 ≥2 页 free chunk 缓冲防止 mmap/munmap 颠簸。
- **before/after**：释放 100% 后 VmRSS **95 MB → 12 MB**（仅比基线高 ~8MB）。

**Phase 2：17 级密集 class（内部碎片上限 25%）**

- **动机**：8 级 class 间距 2×，46B 请求落 64B（浪费 39%）、80B 落 128B（浪费 60%）。
- **改动**：参考 jemalloc（~1.19×）和 TCMalloc（~1.12×）间距，扩为 17 级 `{16,24,32,...,1024}`（~1.25× 几何级数），碎片上限压到 25%。
- **before/after**：峰值 VmSize **97 MB → 89 MB（-8.1%）**，每条目省 8 字节。

**Phase 3：压缩 chunk header（24B → 16B）**

- **动机**：`small_chunk_t` 有废 `reserved` 字段，magic/class_idx/request_size 宽存储。
- **改动**：去 reserved；magic uint32→uint8；class_idx uint16→uint8；request_size uint32→uint16；`next` 指针置首保对齐。
- **before/after**：峰值 VmSize **89 → 81 MB**（与 libc 差距收窄到 11%）。

### Q1. Phase 3 压缩 chunk header：magic/class_idx/request_size 缩小有影响吗？

**结论：没有。三个字段的实际取值范围都远小于字段容量，正确性不受影响。**

| 字段 | 容量 | 实际取值 | 结论 |
|---|---|---|---|
| `magic`（uint8） | 256 | 小 chunk 只用 **1 个值** `CHUNK_MAGIC=0xCC`（`kvs_mem.c:17`）；large/fallback 用独立 uint32 魔数（`kvs_mem.c:18-19`） | 256 ≫ 1，余量充足 |
| `class_idx`（uint8） | 256 | `SMALL_CLASS_COUNT=19`，取值 `[0,18]` | 256 ≫ 19 |
| `request_size`（uint16） | 65535 | `SMALL_MAX_SIZE=1024`，取值 `[1,1024]` | 65535 ≫ 1024 |

逐字段说明（对应代码）：

- **magic**：free/realloc 时只做**相等判断** `chunk->magic == CHUNK_MAGIC`（`kvs_mem.c:344,402`），不需要很多魔数——小 chunk 一个就够了。真正的防误判靠**双保险**：`magic==0xCC` **且** `class_idx < SMALL_CLASS_COUNT`（`kvs_mem.c:344,402`），两条件同时满足才当 custom 小块处理。
- **class_idx**：free 时用它定位 `small_class_t`（`kvs_mem.c:407`）；`class_idx < SMALL_CLASS_COUNT` 的越界检查保证即使头被写坏也不会 OOB 访问数组（`kvs_mem.c:402`）。19 < 256，怎么都不会溢出。
- **request_size**：只在三处用——`realloc` 判断"新尺寸 ≤ 旧尺寸就就地复用"（`kvs_mem.c:516`）、free 时精确记账 `current_requested_bytes`（`kvs_mem.c:404`）、`MEMSTAT` 碎片统计。1024 < 65535，够用。

**真正被"缩小"的是防御强度，不是正确性**：32 位魔数随机命中概率 2⁻³²，8 位降到 2⁻⁸。但 `custom_free` 只被 `kvs_free` 在 `kvs_malloc` 返回的合法指针上调用，配合 `class_idx<19` 检查，实际路径上误判概率为 0——这不是安全边界，是防编程错误的兜底。压缩的收益 = 每 chunk 省 8 字节（24B→16B），1M chunk 省 **8MB**（Phase 3 效果 89→81MB）。

> 注意：`request_size` 是**分配时**才写入（`custom_malloc`，`kvs_mem.c:304`）；`slab_grow_locked` 只给整页预设 `magic + class_idx`（`kvs_mem.c:264-270`）。所以**空闲 chunk 的 request_size 是残留垃圾**，但 `custom_free` 只作用于合法分配指针，读到的一定是分配时写入的值。

**Phase 4：free_stack 索引（16B → 4B，反超 libc）**

- **动机**：链表 free list 每 chunk 需 8B `next` 指针。
- **改动**：per-page `uint16_t free_stack[]` LIFO 索引栈替代链表（页内最多 ~1000 chunks，2B 够索引）；顺带 `total_free_chunks = Σ free_top` 变 O(page_count)。
- **before/after**：峰值 VmSize **80.7 MB < libc 82.8 MB（-2.5%，反超）**，bytes/条目 82.6 < 84.7。

### Q2. Phase 4：per-page `uint16_t free_stack[]` 索引栈怎么做的、为什么够

**数据结构**（`kvs_mem.c:28-36,302,412-413`）：每个 slab 页自带一个 `uint16_t *free_stack`（长度 = `chunks_total`），值是 **chunk 下标**（0..count-1）：

```
分配:  ci = pg->free_stack[--pg->free_top];            // 弹栈（LIFO）        kvs_mem.c:302
释放:  ci = (chunk_ptr - page->mem) / chunk_total;    // 地址差反算下标       kvs_mem.c:411-412
       pg->free_stack[pg->free_top++] = ci;           // 压栈                kvs_mem.c:413
```

页建立时把 `free_stack[i] = i`（0..count-1 全部空闲，`kvs_mem.c:254`）。

**为什么 uint16 够（数学证明）**：需求 = `count ≤ 65535`（uint16 上限）。而

```
count = page_size / chunk_total
chunk_total = sizeof(small_chunk_t) + class_size = 4 + class_size
```

- 最小 size class 是 **8B** → `chunk_total = 4+8 = 12` → `count = 65536/12 = 5461`（`kvs_mem.c:231` 整数除法）。你估算的 5333 是近似（64KB 实为 65536B，65536/12=5461.33 → 5461），方向对：**远小于 65536**。
- 通用下界：`chunk_total ≥ 4`（class_size≥0）→ `count ≤ 65536/4 = 16384 < 65536`。所以**只要页 ≤64KB 且 chunk ≥4B，uint16 永远够**——即使未来加一个 1 字节 class（chunk_total=5 → count=13107）也不溢出。
- 最大 class 1024B：`chunk_total=1028` → `count=65536/1028=63`，更是轻松。

**为什么比链表省**：链表方案每个 chunk 的 header 里要 8 字节 `next` 指针；`free_stack` 是**页级共享**的一个 uint16 数组（整个页一个），chunk 本身不再存指针，所以 `small_chunk_t` 从 16B 压到 4B（`request_size:2 + magic:1 + class_idx:1`）。代价 = 每页一个 `malloc` 的 uint16 数组（class 8 页 ≈ 5461×2B ≈ 10.9KB/页），页回收时一起 `free`（`kvs_mem.c:394`），不是泄漏。效果 = 每 chunk_total 省 12B，峰值 VmSize 反超 libc（80.7 < 82.8 MB）。

**Phase 5：class 8/136 + array 惰性分配（2026-08-02）**

- **动机**：XSET（skiptable）节点做 3 次分配，value=128 时 129B 落 class 160（浪费 24%）、forward level0 8B 落 class 16（浪费 50%），碎片率 14.1%、RSS 94MB。
- **改动**：`SMALL_CLASS_COUNT` 17→19，加 class **8**（接 forward）+ **136**（接 value 129）；`kvs_array_create` 的 1M×16B=16MB 预分配改**首次 SET 惰性分配**。
- **before/after**：XSET 300k 碎片率 **14.1%→5.0%（-64%）**、RSS **94→86MB**（贴平 libc/jemalloc 87MB）；基线 VmSize **36.7→20.3MB**、VmRSS **21→4.6MB**（16MB array 消失）。

### 3.4 弯路

- **"custom 省 libc 6x"（12.4 vs 74.9 MB）是假象，已废弃**：那是 `-n 200000 -c 50 -P 40 -r 200000`（20 万 key）+ 跑完 settle 3s 后读 VmRSS——差异来自 **50 连接缓冲的归还**（custom 缓冲走 mmap 关闭即 munmap，libc 缓冲 free 进堆不 trim 残留），**不是数据密度**。统一 50 连接 + `MEMORY_PURGE` 口径后优势消失（custom 写满 82.8MB ≈ libc 84.7MB）。
- **单连接 ~2300 QPS 假象**：RTT-bound，测不出分配器差异；需多连接/多 P 反推。
- **"XSET 300k custom 144MB / 39% 碎片"是长 key 旧数据的产物**，实测复现不了（实测 94MB / 14.1%）。
- **启动基线 VmSize 高 ≠ 物理内存**：`MAP_STACK|PROT_NONE` 线程栈虚拟预留（`ulimit -s=12.2MB`/线程，RSS 为 0）+ jemalloc arena 虚拟保留；VmRSS 基线仅 4-7MB，三后端一致，非问题。
- **jemalloc 释放后残留 ~2.4MB 清不掉**：arena 元数据 + 保留 extent（`arena.<all>.purge` 清不掉），是 jemalloc 固有开销。

### 3.5 现状（2026-08-24 统一 50 连接口径）


| 后端     | 写满 VmRSS | 释放 VmRSS | 残留 VmRSS | 释放 VmSize | 吞吐（P=1） |
| -------- | ---------- | ---------- | ---------- | ----------- | ----------- |
| libc     | 84,704     | 3,684      | **132 KB** | 94,108      | 127,356     |
| jemalloc | 74,284     | 7,928      | 2,452 KB   | 55,204      | 126,743     |
| custom   | 82,840     | 4,312      | **348 KB** | **32,176**  | 128,271     |

- **吞吐三后端持平（±3%）**：allocator 不是吞吐瓶颈（reactor 单线程，custom 全局锁无争用）。
- **写满峰值受连接缓冲主导**：50 连接 × 1.28MB（inbuf 1MB + out_ring 256KB）= 64MB，数据本身三后端差异小。
- **custom 的价值 = 释放后归还最彻底（slab 页 munmap + 元数据 trim，残留 348KB）+ 可观测碎片统计（MEMSTAT per-class）**。这一点从"最差内存"逆转到"最彻底归还"，是 §3.3 五次优化的结果。
- **2026-08-24 新增**：`custom_free` 每 10 万次加 `malloc_trim`（归还借 glibc 堆的页元数据，custom 残留 2.5MB→0.35MB）；`MEMORY_PURGE` 命令 + `kvs_mem_purge()`。

### 4.3 优化历程

**Step 1：fsync 模式探索（四种模式对比，`483b7d3` 起）**

> 出处：`docs/aof-fsync-modes-analysis.md`、`docs/optimization-history/aof-concurrent.md`。


| 模式                              | P=1   | P=160  | 结论                                                                     |
| --------------------------------- | ----- | ------ | ------------------------------------------------------------------------ |
| 异步逐条（per-command）           | 44.8k | 623k   | 中高 P 落后 Redis（72-94%），480 slot 撑爆后`sq_retry` 空转              |
| **同步逐条**                      | 2.5k  | 2.5k   | **每条命令阻塞 reactor 于 fdatasync，对 P 完全无感**（死锁在串行 fsync） |
| 同步批量                          | ~43k  | 903k   | 高 P 超 Redis 15-51%，但 P=1 落后（RTT 含 fsync）                        |
| **异步批量 group commit（默认）** | ~43k  | 1,312k | **唯一全面超 Redis 的方案**                                              |

> **追问：四种刷盘模式具体怎么做的？**
>
> 四种模式是 `per_command`（逐条 vs 批量）× `sync`（同步 vs 异步）的笛卡尔组合（`persist_append_prepare` 分派，`kvs_persist.c:914-994` + `docs/aof-fsync-modes-analysis.md`）：
>
> | 模式 | 配置 | 实现 |
> |---|---|---|
> | **异步批量**（group commit，现默认） | `per_command=0, sync=0` | 命令 append 到 `g_aof_buf`；每 epoll 周期结束 `persist_flush_pending()` 提交 **linked write+fsync 到 io_uring**（异步不等），响应立即发 |
> | **异步逐条** | `per_command=1, sync=0` | `persist_append_prepare` 每条命令 append 后**立即** `persist_flush_pending()`（异步 io_uring 提交，不等） |
> | **同步批量** | `--aof-fsync-sync-batch`（`per_command=0, sync=1`） | `persist_flush_pending()` 里 `sync=1` 改为**直接 `pwrite + fdatasync`（阻塞等落盘）**，批量攒满 epoll 周期一次 |
> | **同步逐条** | `--aof-fsync-sync`（`per_command=1, sync=1`） | `persist_append_prepare` 逐条分支 `sync=1` 调 `persist_sync_append_write()`：每条命令**直接 `pwrite+fdatasync`（阻塞）** |
>
> ```c
> if (g_cfg.aof_fsync_per_command) {
>     if (g_cfg.aof_fsync_sync) persist_sync_append_write();  /* 同步逐条 */
>     else                      persist_flush_pending();      /* 异步逐条 */
>     return KVS_PERSIST_OK;
> }
> if (g_cfg.aof_fsync_sync) { persist_sync_append_write(); return; }  /* 同步批量 */
> /* ... 否则异步 io_uring 批量（默认） ... */
> ```
>
> 实测（`aof-fsync-modes-analysis.md` §3.1）：异步批量 ~89k（±12%）、异步逐条 ~60k（±12-15%）、同步批量 ~71k（±2.4%）、同步逐条 ~4k（无批处理摊薄 fsync）。**异步批量峰值最高**（89k）但波动大（fsync 抖动被 run-ahead→io_uring ring 填满→突发放大）；**同步批量最稳**（±2.4%，fsync 抖动被批内平均）但峰值低。同步逐条不可用（每条命令一次 fsync，吞吐暴跌）。

> **追问补充：为什么异步逐条接近批量、同步逐条低到 4k？回复客户端时间不同吗？**
>
> 核心差异在**回复客户端的时间（是否等 fsync）**：
> - **异步**（批量/逐条）：回包**不等 fsync**（io_uring 异步提交，回包先发）→ 客户端 RTT **不含 fsync**，主循环生产节奏由 `MAX_OUTSTANDING=16` 槽背压决定（≈ fsync 完成率 × 批大小）。逐条只是**提交频率高**（每命令一次 io_uring submit、ring 压力大、480 slot 撑爆后 `sq_retry` 空转），所以比批量略低（60k vs 89k）但**同量级**；
> - **同步**（批量/逐条）：回包**等 fsync**（主线程阻塞 `pwrite+fdatasync`）→ 客户端 RTT **含 fsync**。同步逐条每条命令一次 fsync **串行阻塞** → 吞吐 = 1/fsync延迟 ≈ 1/250µs ≈ **4k**（fsync 是每命令闸门，无任何摊薄）。
>
> **QPS 按客户端发→收回复计算**：同步逐条每条回复都等一次 fsync，客户端 RTT 最大 → 最慢；异步不等 fsync → 快。

**Step 2：AOF 独立线程 + 先回复（reply-first，`98eeefc`，2026-08-07）**

- **动机**：异步批量虽好，但回包仍等 fsync（durable-before-reply），P=1 单请求 RTT 恒含 fsync 延迟。
- **改动**：AOF 写入挪到独立线程（io_uring），回包不等 fsync，回包队列 ≤`MAX_OUTSTANDING=16` 批；write-in-place 槽无深拷贝。
- **before/after**（P-sweep，出处 `docs/superpowers/bench/2026-08-06-aof-thread-reply-first.md`）：


| P   | 新实现(reply-first) | 基线(README 08-04) |      变化 |
| --- | ------------------- | ------------------ | --------: |
| 1   | 76,476              | 42,717             |  **+79%** |
| 10  | 419,463             | 373,692            |      +12% |
| 40  | 796,178             | 891,266            | **−11%** |
| 160 | 1,054,852           | 1,024,590          |       +3% |

- 最大收益在 P=1（+79%）；**P=40 出现 −11% 回退**（多次复测确认非噪声，根因未收敛），属未解决的回退。

**Step 3：攒批窗口 group commit（`aof_group_commit_window_us=2000` 默认，2026-08-11）**

- **瓶颈定位（数据分析三步）**：
  1. fdatasync 微基准中位 **362µs** / p99 1ms → fsync 延迟 ~0.4-1ms 量级；
  2. AOF always `-c 50→100`（批大小翻倍）75.9k→**92.1k（+22%，随批缩放）**→ fsync 率受限；AOF 关闭 ~125k→118k 不变 → 纯 CPU；
  3. 吞吐模型 `= 批大小 × fsync 率 = 50 × (1/0.66ms) ≈ 76k` **与实测吻合**。
- **改动**：`persist_flush_pending()` 改窗口感知——窗口未到且槽未满则跳过 handoff 只 reap，攒多周期共享一次 fsync；窗口=0 行为与旧版一致（可回退）。
- **before/after**（窗口对照，300 档）：window=0 **75,706** → **window=2000µs 115,781（+53%）** → window=4000 113,849（顶到 CPU，不再涨）。

> **追问：瓶颈定位三步怎么分析出是 fsync 的问题？窗口和槽又是什么？**
>
> **（1）三步分析（`docs/data_analysis/aof-group-commit.md` §2）——核心是"对比实验 + 模型验证"**：
>
> | 步骤 | 实验 | 结果 | 排除/锁定 |
> |---|---|---|---|
> | ① fsync 延迟量级 | fdatasync 微基准（1KB 追加×100） | 中位 **362µs** / p99 1ms | fsync ~0.4-1ms 量级 |
> | ② 批大小 → 吞吐（AOF always） | `-c 50 → 100`（批翻倍） | 75.9k → **92.1k（+22%）** | **吞吐随批大小缩放 → fsync 率受限** |
> | ②' 对照组（AOF 关闭） | 同 `-c 50 → 100` | ~125k → ~118k（不变） | **纯 CPU 上限，无 fsync 闸门** |
> | ③ 吞吐模型 | `批大小 × fsync 率 = 50 × (1/0.66ms) ≈ 76k` | 与实测吻合 | 模型确认 |
>
> **关键逻辑**：如果瓶颈是 CPU，`-c 50→100`（批翻倍）吞吐应不变（CPU 上限）；实测 **AOF always 随批缩放 +22%**，而 **AOF 关闭不变**——说明 AOF always 的吞吐被"**批大小 × 每秒能完成多少批 fsync**"钉死，不是 CPU。这就是"fsync 率受限"的证据。
>
> **（2）槽（slot）和窗口（window）**：
>
> - **槽** = AOF 批量写入的单位缓冲。写命令 `memcpy` 进当前槽 `g_cur_slot->aof_buf`（64KB 起、动态翻倍到 4MB，`kvs_persist.c:970-983`）；槽 `handoff` 后由 AOF 线程 io_uring 提交（write+fsync）。`MAX_OUTSTANDING=16` = 最多 16 个槽在途（背压界住崩溃窗口）。
> - **窗口**（`aof_group_commit_window_us`）= 攒批时间窗。`persist_flush_pending()`（reactor 每轮末尾）窗口未到且槽未满 → **跳过 handoff 只 reap**，多攒几个 epoll 周期共享一次 fsync（`kvs_persist.c:1078-1088`）；窗口=0 行为与旧版一致（可回退）。
> - **为什么窗口增大提高 QPS**：`吞吐 ≈ 批大小 × fsync 率`。window=0 时每 epoll 周期 flush（批 = 一周期命令 ≈ 50 条）、fsync 率 ~1500/s（0.66ms/次）→ 50×1500 = 76k；window=2000µs 攒批后**批变大**（2000µs 内攒的命令），fsync 率不变但批大 → 115.8k。**本质 = 用更大的批摊薄 fsync 次数**，把瓶颈从 fsync 率挪回 CPU 上限。
>
> **追问补充：fdatasync 微基准怎么做？吞吐模型是公认的吗？**
>
> **fdatasync 微基准**（`aof-group-commit.md` §2）：写一个 1KB 文件（`pwrite`）→ `fdatasync` → 循环 100 次，测每次延迟（KVM /dev/sda5 ext4），中位 **362µs** / p99 1ms。
>
> **为什么"批翻倍 → QPS 增"能证明 fsync 率受限**：核心是**对照组**。如果瓶颈是 CPU，`-c 50→100`（批翻倍，每批命令数翻倍）吞吐应**不变**（CPU 上限）；实测 **AOF always 随批缩放 +22%**，而 **AOF 关闭对照不变**（~125k→118k）——对照组排除了 CPU，只剩"每批一次 fsync、批越大每批摊的命令越多"这个解释。
>
> **吞吐模型**：`吞吐 = 批大小 × 批完成率`，批完成率 = 1/fsync 延迟。这是 **Little's Law 在 fsync 场景的变体**（每批"在途时间" ≈ fsync 时间，吞吐 = 批量/在途时间）——排队论/吞吐计算的通用公式，不是 Redis 特有、也不是自行发明。窗口=0 时模型预测 76k 与实测吻合，就是模型有效性的验证。

**Step 4：稀疏流量修复（2026-08-12）**

- **问题**：window=2000 下孤立命令要等 reactor 下次唤醒（epoll 100ms 超时）才 flush，**稀疏崩溃窗口膨胀到 ~105ms**。
- **改动**：`persist_aof_pending_flush_ms()` 让 `epoll_wait` 超时 = min(100, 窗口剩余)。
- **before/after**：稀疏单条写落盘 **~105ms → ~6.6ms**（≈ 窗口 + 唤醒 + fsync）。

### 4.4 弯路

- **"落盘才回包 + io_uring"是负结果（2026-08-12）**：一旦回包必须等 fsync，主线程等在那里没有重叠，io_uring 的异步优势用不上反而多付 handoff→AOF 线程→submit→CQE→reap→fence 的 IPC 往返，**比直接 `pwrite+fdatasync`（同步批量）还慢（36k vs 41k）**。**核心洞察：io_uring 的价值恰在"不等"（先回复 + 异步重叠）**，该实验已回退。
- **未绑 taskset 的测量波动假象**：AOF always 的"66-88k 波动"部分来自客户端裸跑虚高到 ~82k；服务端+客户端都绑核后波动降到 CoV 2-7%。

> **追问：为什么绑核能降低波动、不绑核波动大？**
>
> 4 vCPU 的 VM 上，不绑核时进程/线程（服务端、redis-benchmark 客户端、以及 vscode/claude/mysqld 等后台）会在核间**随意迁移**：
> - **调度抖动**：线程被调度到不同核 → 上下文切换 + 缓存（TLB/L1/L2）全部失效重填；
> - **核间争抢**：服务端和客户端抢同一个核 → 互相拖慢，吞吐不稳定（客户端裸跑还能抢到更多核 → 虚高到 ~82k）；
> - **softirq 迁移**：网卡软中断随机落核，与主线程争 CPU。
>
> `taskset` 把服务端固定到核 2/3、客户端固定到核 0 后：消除迁移抖动 + 核间争抢 + 保证 cache 亲和，AOF 波动从 **±12-20% → CoV 2-7%**。**不绑核时"66-88k 波动"部分是客户端裸跑抢核的假象**，绑核后才是服务端真实能力。

- **先回复改造 P=40 回退 −11%**：多次复测 762-835k 均低于基线，非噪声；方向指向先回复窗口背压与槽轮转/io_uring 提交在 P=40 段的交互，**根因未收敛**（诚实记录）。
- **方法论坑**：单线程客户端上限、ms 精度量化假相等（详见 §2.2）；验证崩溃窗口**不能只看持续负载，必须测稀疏单条写**。

### 4.5 现状（2026-08-25，memtier + populate 1M）


| 配置                                    | HSET (Ops/s) | vs baseline         |
| --------------------------------------- | ------------ | ------------------- |
| **kvstore** AOF 关闭（`--aof-disable`） | 202,138      | baseline            |
| **kvstore** AOF always                  | **175,221**  | **87%**（仅 −13%） |
| **Redis 7.2.9** 无 AOF                  | 187,382      | baseline            |
| **Redis** AOF always                    | 75,124       | 40%（−60%）        |

- **kv AOF always 是 Redis 的 2.33×（175k vs 75k）**；kv AOF 相对关闭仅 −13%（fsync 瓶颈已被攒批窗口消除），redis 掉到 40%。
- 崩溃窗口稳态 ~2.5ms / 最坏 ~10ms；批间 CoV 1.4%（旧逐条 16-34%）。
- **从 63.5k（-52%）到 175.2k（-13%，2.33× Redis）**，是 AOF 这条线 4 步优化 + 负结果排除的最终成绩。

## 5. 性能测试：SAVE 全量持久化

> README 位置：「持久化性能基准 → SAVE 性能测试」。测试脚本：`tools/bench/run_save_bench.py`。

### 5.1 测试方法

Hash 引擎（HSET 去重键）→ populate N 键（单连接顺序键）→ 多连接 `memtier -t 2 -c 50 --test-time` 测稳态写 QPS；SAVE 计时用 `redis-cli SAVE` + 高精度时钟。数据规模 100w / 10w / 1w / 1k。

### 5.2 起点：初测数据有多差（2026-06-11）

- **SAVE 100w 耗时 ~3.9s**（3,964ms）——dump 只有 19.6MB，折合 ~5MB/s，**慢在每 key 6-7 次 write syscall（100w ≈ 650 万次 write）**。
- **写入 QPS 更差**：渐进式 rehash 之前 hash 引擎 100w 写入只有 **~21k**；渐进式 rehash 后 129,685（6.2×），但 SAVE 本身还是 ~3.9s（纯 I/O，不受写入优化影响）。
- 早期"有效 QPS"口径（`数据量/(写入时间+SAVE 总耗时)`）100w 只有 85k——SAVE 占了总时长的 1/3。

### 5.3 优化历程

**Step 1：渐进式 rehash（写入路径，2026-06 前后）**

- **动机**：hash 表一次 rehash 到顶，插入退化。
- **before/after**：100w 写入 QPS **~21k → 129,685（6.2×）**；有效 QPS ~19k → 85k（4.5×）。出处：`docs/save-benchmark.md`。

**Step 2：4MB 用户态写缓冲（`05b3ae4`，2026-07-28）**

- **动机**：SAVE 慢在每 key 一次 `write()`。
- **改动**：`kvs_dump_to_fd()` 加 4MB 用户态写缓冲——遍历引擎 `memcpy` 到缓冲，满或结束才 `write()`。
- **before/after**：write syscall **每 key 6-7 次 → 每 4MB 1 次**（100w ≈ 5 次 vs 优化前 ~650 万次）；SAVE 100w **~3.9s → ~130ms（约 30×）**。出处：`docs/save-analysis.md`。

**Step 3：SAVE 1k 冷启动优化（`f474fc6`，2026-08-03）**

- **before/after**：1k 数据量 SAVE+always 表口径 36k → 40.75k（干净重启口径）。

> **追问：1k 数据量的写 QPS 为什么只有 100w 的一半？怎么优化的？**
>
> **数据量越小，连接建立开销占比越高**。kvstore 每连接建 `inbuf`(1MB) + `out_ring`(256KB) 缓冲，若用 `calloc` 清零 = **50 连接 × 1.3MB = 65MB 清零 + 1.6 万缺页**（`reactor.c:128-130` 注释）。大数据量（100w）时这个一次性成本被海量写入摊薄；**1k 数据量写入只有 ~0.1s，连接建立的开销占比极高 → QPS 被拖到 31.6k（约大数据的 1/4-1/2）**。
>
> 优化（`f474fc6`/`4c39b8c`）：inbuf/out_ring **一次 `kvs_malloc` 合并分配 + 不清零**（两个缓冲都"先写后读"、len 从 0 计数，无读到脏数据风险；不清零则页按需分配，省 65MB 清零 + 缺页）。**1k 冷启动写 QPS 31.6k → ~117k（追平 redis，接近 100w 量级）**。这也是 §3.1 网络层"I/O 缓冲不清零"优化的另一面——**冷启动小数据量场景收益最明显**。

### 5.4 弯路

- **早期把"有效 QPS"当主指标**：SAVE 一次就把写入 + 落盘混在一起，掩盖了"写入其实很快、SAVE 慢在 syscall"的真相；后来拆开测（写 QPS 与 SAVE 延迟分开）才定位到 write syscall。
- **"SAVE 耗时不变（纯磁盘 I/O）"曾误导**：渐进式 rehash 前后 SAVE 都是 ~3.9s，一度以为 SAVE 是磁盘上限；实际上 4MB 写缓冲证明瓶颈是 syscall 数，不是磁盘带宽（19.6MB/130ms ≈ 150MB/s，远超之前 5MB/s）。

### 5.5 现状（2026-08-25，独立批口径）


| 场景 | 写 QPS kv | 写 QPS redis | kv/redis | SAVE 耗时      |
| ---- | --------- | ------------ | -------- | -------------- |
| 100w | 202,126   | 192,230      | 1.05     | **~123-140ms** |
| 10w  | 208,896   | 190,596      | 1.10     | ~10.8ms        |
| 1w   | 214,665   | 192,712      | 1.11     | ~4.0ms         |
| 1k   | 209,832   | 185,770      | 1.13     | ~3.6ms         |

- **SAVE 100w 是 Redis 的 ~7× 快**（kv ~140ms vs Redis ~1039ms，7.4×）；kv dump 100w 仅 ~40MB vs Redis ~45MB（存储更紧凑，早期口径 19.6B/条目 vs 34.4B/条目同样成立）。
- SAVE 开销占比从优化前 33% → **~3%**（100w 写入 ~5s @ 202k QPS + SAVE 0.14s；早期 125k 口径下为 1.5%）。
- 各数据量写 QPS 持平（~202-214k）——P=1 下 per-command 成本由分派/解析主导，hash 表大小影响很小；100w 的 202k 与 AOF/Pipeline P=1 HSET（202k）一致（统一标准）。

### 6.3 优化历程

**Step 1：编译 + 12 项 pipeline 热路径优化清单**

- `-march=native -funroll-loops`、`likely/unlikely` 分支预测、`fast_itoa` 手写整型转换、ECHO/PING 合并 queue_bytes、strtol→内联解析、TCP_NODELAY、`kvs_ascii_upper` 去 locale 查找、响应缓冲 VLA 栈分配、`strlen→argl`、解析器 no_scratch、`epoll_events` 缓存、queue_bytes 延迟 EPOLLOUT 注册。
- 出处：`docs/optimization-history/pipeline-analysis.md`。

**Step 2：reactor 统一写（`46a8c9c`，2026-08-01）**

- **动机**：每请求立即 send 摊不掉固定开销。
- **改动**：事件循环末尾批量 drain（对齐 Redis `beforeSleep`），一次 `send` 发整批响应。
- **before/after**：低 P（RTT 受限）大幅提升，ECHO/HSET 从此反超 Redis；ECHO P=1 从 ~101% → 119%。

> **追问：reactor 统一写（`46a8c9c`）仔细讲一下**
>
> **优化前**：一条会回包的命令要经过**两轮事件循环 + 2 次 epoll_ctl**——第 N 轮 `EPOLLIN` → `on_read` 读 + `queue_bytes` 把响应写进 out_ring → `queue_bytes` 里"空→非空"注册 `EPOLLOUT`（`reactor.c:68`）→ 第 N+1 轮 `EPOLLOUT` → `on_write` 真正 `send` → 发完再 MOD 回 `EPOLLIN`。perf 实测 `epoll_ctl` 占 ECHO 路径 **~13%**、HSET **~7%**（`reactor.c:204`）。
>
> **优化后**（对齐 Redis `beforeSleep`）：读路径只置 `defer_epollout=1`（`reactor.c:176`）抑制 `queue_bytes` 的 EPOLLOUT 注册（`reactor.c:68` 的 `&& !c->defer_epollout`）；命令解析完**不立即 send**，等**每轮事件循环末尾 `flush_conn_output(NULL)` 统一 flush**（`reactor.c:393`，遍历 fdmap 把所有有 pending 输出的连接 `send` 一次）。一次写不完（EAGAIN/慢客户端）→ `on_write` 末尾按剩余量注册 `EPOLLOUT` 兜底（`reactor.c:231`）。
>
> **效果**：正常情况一条命令 **0 次 `epoll_ctl`**（`mod_events` 有"mask 相同就跳过"守卫，`reactor.c:38`）。50 客户端各发一条 PING：优化前 2 轮事件循环 + 100 次 epoll_ctl，优化后 1 轮事件循环 + 0 次 epoll_ctl。低 P（RTT 受限）收益最大（ECHO P=1 从 ~101% → 119%）。

**Step 3：accept4 + inbuf/out_ring 合并分配（`4c39b8c`，2026-08-03）**

- **改动**：连接建立路径 accept4 + 连接缓冲合并分配，降低每连接开销。

> **追问：accept4 + inbuf/out_ring 合并分配（`4c39b8c`）仔细讲一下**
>
> 连接建立路径的两个开销：
> 1. **accept4**：一次系统调用完成 `accept + SOCK_NONBLOCK + SOCK_CLOEXEC`，替代 `accept` + 2 次 `fcntl`（`reactor.c:108-109`），省 2 个 syscall/连接；
> 2. **缓冲合并分配**：`c->inbuf = kvs_malloc(INBUF_CAP + OUT_RING_SIZE)`（1MB + 256KB），`c->out_ring = c->inbuf + INBUF_CAP`（`reactor.c:131-137`）——两个缓冲首尾相接放同一块内存，**省一次 `kvs_malloc`（可能一次 mmap）+ 不清零省 calloc 清零**（50 连接 = 65MB 清零 + 1.6 万缺页）。
>
> 收益：每连接建立省 2 次 fcntl + 1 次 malloc + 65MB/50 连接的清零。**大数据量下不明显（摊薄了）**，**冷启动/小数据量（如 SAVE 1k）场景收益大**（31.6k → ~117k，见 §5.3 Step 3）。

**Step 4：真 3 参 HSET + rehash（`652aaa7`）**：HSET 语义对齐 + hash 引擎 rehash，消除写入退化。

**Step 5：命令分派/应答 fast path（2026-08-25 三项，未提交工作区，README 已记录）**

- **HSET/HGET/HDEL/HMOD 分派 fast path**（`goto engine_dispatch` 绕开 ~35 次 strcmp）：HSET **P=160 2.16M → 3.10M（+44%）**。
- **reactor 读路径去掉冗余 EPOLLOUT 预注册**（每命令省 2 次 epoll_ctl）：ECHO/HSET **+31%**。
- **repl_broadcast 无副本早退**（省 mutex+snprintf）：~+1.5%。
- **SET/HSET 成功应答静态字面量直写**（5 字节替换 snprintf）：HSET argc=3 真路径 **+12.6% P10 / +3% P160**。
- 出处：§10 ECHO 热点定位 + README「Pipeline 批量性能测试」注。

> **追问：命令分派 fast path（2026-08-25，未提交工作区）仔细讲一下**
>
> `handle_parsed_command` 的控制命令链是一长串 `if(!strcmp(cmd, "PING")) ... if(!strcmp(cmd,"ECHO")) ...`（`kvstore.c:1284-2041`），HSET/HGET/HDEL/HMOD 要走完 **~35 次 strcmp** 全部落空后才到引擎区（`engine_dispatch`）。
>
> 优化：在控制命令链**之前**加一个检查（`kvstore.c:1274-1282`）——`argl[0]==4 && cmd[0]=='H'` 且 `cmd[1..3]` 是 `SET/GET/DEL/MOD` → **直接 `goto engine_dispatch`**，绕开整个控制命令链的 strcmp：
>
> ```c
> if (argl[0] == 4 && cmd[0] == 'H') {
>     const unsigned char *sc = (const unsigned char *)cmd;
>     if ((sc[1]=='S' && sc[2]=='E' && sc[3]=='T') ||
>         (sc[1]=='G' && sc[2]=='E' && sc[3]=='T') ||
>         (sc[1]=='D' && sc[2]=='E' && sc[3]=='L') ||
>         (sc[1]=='M' && sc[2]=='O' && sc[3]=='D'))
>         goto engine_dispatch;
> }
> ```
>
> **为什么收益大（+44%）**：分派是**每命令固定成本**（不随 Pipeline 深度 P 摊薄），P=160 时每处理一条 HSET 都要付这 35 次 strcmp；`goto` 后只比较 4 个字符。语义与正常落空到引擎区完全一致（这些命令本就不匹配任何控制命令），只省 strcmp。HSET P=160 **2.16M → 3.10M（+44%）**。

### Q3. §6.3 Pipeline 优化历程：效果最好的优化点

按"每命令固定成本降幅"排序（数据来自 README 2026-08-25 与原始数据）：

| 排名 | 优化 | 效果 | 为什么收益大 |
|---|---|---|---|
| 1 | **HSET/HGET/HDEL/HMOD 分派 fast path**（`goto engine_dispatch` 绕开 ~35 次 strcmp） | HSET **P=160 2.16M→3.10M（+44%）** | 分派是**每命令固定成本**，P 越大越难被摊薄，收益随 P 放大 |
| 2 | **reactor 读路径去冗余 EPOLLOUT 预注册**（每命令省 2 次 epoll_ctl） | ECHO/HSET **+31%** | `epoll_ctl` 是 syscall，perf 实测占 ECHO ~13%、HSET ~7%（`reactor.c:204`） |
| 3 | **SET/HSET 成功应答静态字面量直写**（`+OK\r\n` 5B 替换 snprintf） | +12.6% P10 / +3% P160 | snprintf 固定开销在低 P 摊不掉，P 越低收益越大 |
| 4 | **reactor 统一写**（`beforeSleep` 批量 drain，`46a8c9c`） | 低 P 大幅提升，ECHO 从此反超 Redis | 省每命令 send 的固定开销 + 2 次 epoll_ctl |
| 5 | 12 项编译/热路径微优化（march=native、fast_itoa、VLA 栈分配、TCP_NODELAY 等） | 单点小、累积可观 | — |

**规律**：收益最大的都是**"减少每命令固定开销"**类（分派 strcmp、epoll_ctl、snprintf、syscall 数）——因为它们不随 Pipeline 深度 P 摊薄；P 越低（RTT 受限）则"写路径 syscall 数"越关键。对照：AOF 攒批窗口是**另一类**（摊薄 fsync），针对的是持久化路径，不是命令分派。

### 6.4 弯路

- **ECHO P=20 比值谷底（~101%）是测量巧合**：P=20 处单客户端上限 ≈ redis 服务端速率，kv 被客户端压住、redis 自身也到此——不是服务端曲线交叉（证据：比值随 P 非单调，而 no-AOF HSET 基础优势随 P 单调升）。
- **ms 精度量化假相等**：ECHO P=20 曾报告 `2,083,333 == 2,083,333`，回 8 轮原始数据核对只有 1/8 对相等，kv 实际高 1.9%。
- **单线程客户端上限**：kv ECHO 全 P 被单客户端封顶，双客户端 +36-40%；**换 memtier 双线程才测出"kv 全面超 redis"的正确曲线**。
- **空表测"100w"是虚的**：memtier 多连接随机键跨连接碰撞只写 ~2 万键；populate 1M 后 P=1 HSET（202k）才与 AOF/SAVE 100w（202k）自洽一致。

## 7. 性能测试：eBPF 主从增量转发（同机）

> README 位置：「eBPF fentry+fexit 主从转发 QPS 对比」。完整历程：`docs/ebpf-forwarding-optimization-journey.md`、`docs/superpowers/bench/2026-08-07-repl-fwd-thread.md`。

### 7.1 测试方法

同机 harness（master/slave/proxy 同一台 KVM，loopback）；master 钉 CPU2；客户端 memtier `-t 2 -c 50`；`SKIP_IRQ_PIN`；交错 3 轮中位。三种模式：**none**（纯 echo，无复制）、**sync**（master 同步转发到 slave）、**ebpf**（BPF 捕获 → ebpf-proxy 独立进程 → 转发）。

### 7.2 起点：初测数据有多差

**kprobe 方案（最初）在跨机下全面落后 sync**（64B payload，出处 `benchmark-methodology-qa.md` Q5）：


| mode       | QPS        |     vs sync |
| ---------- | ---------- | ----------: |
| none       | 29,259     |          — |
| sync       | 22,242     |          — |
| **kprobe** | **15,556** | **−30.1%** |

- 后续优化后 kprobe 仍落后 sync（journey 记录 64B −15.8%、128B −32.8%、256B −38.5%），仅 512B +16.6% 唯一反超。
- **根因**：kprobe/kretprobe 在每个 `tcp_recvmsg` 上触发两次 BPF（entry+return，~3-5µs/次）+ `bpf_probe_read_user` 拷贝，拖慢主 echo 路径；异步转发的并行收益被 BPF hook 开销抵消。
- 出处：`ebpf-forwarding-optimization-journey.md` + `benchmark-methodology-qa.md` Q5。

### 7.3 优化历程（6 次迭代）

**迭代 1：fentry/fexit（trampoline 替代 kprobe）**

- **思路**：BPF trampoline 开销比 kprobe 低 ~90%。
- **结果**：fentry QPS 仍 **0/7 超 sync**（64B −22.1%、256B −11.9%、512B −22.1%、1024B −26.1%）。
- **教训**：**只要 BPF hook 挂在主 I/O 路径（tcp_recvmsg）上，不管 hook 机制多快，累积开销都拉低 QPS**，需完全绕过主路径。

**迭代 2：sockmap sk_msg tee（尝试 + 放弃）**

- **不可行**：`bpf_msg_send_data` **不存在于任何已发布内核**（5.15/6.1/6.6 均确认）。sockmap/sk_msg 只有 redirect（互斥），不能 clone/tee。

**迭代 3：用户态异步转发（非 eBPF）**

- **结果**：5/7 payload 超 sync（64B +2.6%、256B +36.4%、1024B +27.5%）——但这是"去掉 BPF"的纯用户态多线程，不是 eBPF 方案。

**迭代 4：TC BPF `bpf_clone_redirect` + VXLAN**

- **结果**：与 sync 持平（±13% 噪声内）。跨 VM 网络 RTT（~0.5ms）是绝对瓶颈，TC 的零主路径优势被网络延迟掩盖。踩了 tc BTF 兼容、loopback 绕过 ens33、SSH 后台管理三个坑。

**迭代 5：ebpf-proxy 独立进程（最终架构）**

- **思路**：把 BPF 从 master 主进程剥离到独立进程；ringbuf 消费者在 proxy 进程。
- **关键优化**：移除 kretprobe 热路径 REPLSYNC/REPLDONE 字符串扫描（~110+ 次 8 字节比较）；移除 stats 原子计数；ITER_UBUF + bounded-size 拷贝（64B vs 之前 8192B）；Slave/Client 独立进程防 PID 反馈循环。
- **结果**：kprobe 开销降到 ~5%，仅慢 sync ~5%。

**迭代 6：fentry+fexit + batch writev + 独立转发线程（`refactor/fentry-fexit-optimize` 分支）**

- BPF 改 **fexit-only**（`ctx[5]` 直接取 `tcp_recvmsg` 返回值，kernel 6.1.176 实测；旧 fentry 存 `count_before`/fexit 算差值的 workaround 已删，`e9d35c3`）；**PERCPU_ARRAY→HASH map**（key=pid_tgid，防 PREEMPT CPU 迁移丢数据 ~45%）；转发批量 `writev`（BATCH_MAX=64）；ringbuf poll 5ms→1ms；libbpf 0.5→1.5 静态链接。
- **结果**：小负载与 sync 持平，大负载 **4KB +37%**（sync 的 4KB slave write 跨机延迟卡住下一个 read，ebpf 异步转发消除阻塞）。
- **再往后**：harness sync 转发改独立线程 + 批量 writev + 环形缓冲（`1e921b1`，sync 跨机 **56k→80k，+84%**）。

### Q4. §7.3 迭代 1（fentry/fexit）与迭代 5（ebpf-proxy）

**（1）fentry/fexit 每次 `tcp_recvmsg` 触发几次 BPF？为什么比 kprobe 好？**

**次数一样多——都是 2 次**：

- kprobe/kretprobe：每次 `tcp_recvmsg` 触发 **2 次** BPF（kprobe entry + kretprobe return）；
- fentry/fexit：同样 **2 次**（旧实现：fentry 存 `msg_ptr + count_before`、fexit 算差值；**当前 fexit-only**：`ctx[5]` 直接取 `tcp_recvmsg` 返回值，kernel 6.1.176 实测，`repl_client_capture.bpf.c:115-117`，不再需要 fentry）。

**优势不在次数，在单次开销**：

| 机制 | 单次开销 | 说明 |
|---|---|---|
| kprobe/kretprobe | **~3-5µs** | 动态插桩：指令替换 + `pt_regs` 全上下文压栈 + kretprobe 实例复用开销 |
| fentry/fexit | **~0.3-0.5µs**（约 1/10） | BPF trampoline：`__fentry__` NOP 槽直接跳转，CC=0，无 `pt_regs` 压栈 |

所以 fentry+fexit 把"每次客户端读的 2 次 BPF 开销"降到 kprobe 的 ~1/10。**但绝对开销仍在**——fentry 结果仍 **0/7 超 sync**（64B −22.1%、1024B −26.1%），因为只要 hook 挂在主 I/O 路径（`tcp_recvmsg`）上，就要为**系统全局**（含 SSH、其他服务）每次 recv 付 BPF 执行代价。**教训：挂主路径的 BPF 再快也拉低 QPS，必须绕过。**

**（2）迭代 5 ebpf-proxy 独立进程为什么有效？**

把 BPF 的**消费者**搬出主进程，效果的关键在四点：

1. **ringbuf 消费/转发 CPU 移走**：master 进程只做 echo，不再 poll ringbuf + 转发；proxy 进程单独吃捕获数据的消费 + 转发 CPU。
2. **转发可批量**：proxy 用独立转发线程批量 `writev`（≤256 节点 / ≤512KB），消除每命令 send 段开销；转发阻塞不再卡 master 的 recv 循环。
3. **BPF hook 开销可控**：master 每次 recv 仍付 fexit 捕获（~0.3-0.5µs + ringbuf 写），但被限制在 bounded-size（`MAX_RECV_BYTES=32764`，保证不截断）+ PID 过滤（只捕 master 进程）。
4. **与主路径解耦**：proxy 慢时 master 只受"背压标志停手"（`client_ctl[4]/[6]` + `usleep(100)`）影响，不阻塞主 echo 循环。

**效果**：kprobe 落后 sync 8-39% → ebpf-proxy ≈ sync（慢 5% 内）；配合转发线程 + 环形缓冲后跨机 sync **56k→80k（+84%）**（`1e921b1`）。**诚实结论**：ebpf 同机最终仍是 `sync ≈ ebpf < none`（都要转发同一份数据，物理必然），ebpf 的价值是"**无损转发**"（背压 + bounded-size + 独立进程），不是"比 sync 快"。

### 7.4 弯路

- **"ebpf 28k→48k（+72%）超 sync"是未绑核假象**（`a595b78` 曾这样记录）：服务器用全部 4 核（含客户端核）才达到；按 README 方法论（服务器 CPU2）真实为 ~48k = None 的 65%，sync ~31k。**绑定核隔离客户端后方向才可信。**
- **历史 README 08-04 的 "ebpf/sync ≈ none 的 50%"（64/128/256/512B 全档）是单核共享假象**：旧 harness「50 线程 per-conn 全 pin CPU2 + 转发在 handler 内联」+ 客户端经 popen 继承 `--cpu 2` 亲和**实际与 master 同核** → master+50 handler+客户端+转发全挤 CPU2 一个核，sync/ebpf 额外转发再分掉 master 的核 → 稳定 ~51%/~55%。**瓶颈是单核 CPU 分享、与 payload 无关**（loopback 传 payload 相对客户端事件循环开销极便宜），所以 64-512B 比值不变。修复（转发/proxy pin CPU0、客户端 pin CPU3、固定 keyrange、环形缓冲去 cond_signal）后 sync 49%→**84%**、ebpf 31.5%→**72%**，最终同机 ≈ none（0.94-0.98）。调查全记录：`docs/superpowers/bench/2026-08-10-harness-fwd-thread-qps.md`。
- **2026-08-25 的 "sync≈none" 是第二个测量 bug**：harness 的 HSET 检测只认 redis-benchmark 的大写 `*4 $4 HSET`，memtier 发小写 `*3 $4 hset` → sync 模式从不触发转发（batch_start 不设、fwd_enqueue 不调用），**sync 列实为"没转发的 none"**。已修复（HSET 检测大小写不敏感 + argc≥3）。
- **内核 6.1 三个适配坑**：`struct iov_iter` 改 `ITER_UBUF`（nr_segs=0）；`bpf_probe_read` 对内核内存静默失效（换 `bpf_probe_read_kernel`）；fexit `ctx[0]` 在 6.1 不是 retval（改差值计算）。
- **PERCPU_ARRAY 丢数据 ~45%**：PREEMPT_DYNAMIC 下 fentry 和 fexit 之间可能迁到不同 CPU，PERCPU 读到错误 slot 直接跳过；改 HASH map key=pid_tgid 后 fexit 消费即删。

- **P>40 后 sync/ebpf 相对 none 比值下降（根本原因 = 转发线程跨机 writev 路径）**：
  - **FWD_DISCARD=1 实验（2026-08-30，决定性）**：harness fwd 线程**不 writev 到 129**（只入队+丢弃），sync P=160 = **2.92M ≈ none（3.10M）**；正常（writev 到 129）= 2.24M。→ **sync 跨机瓶颈 = fwd 线程跨机 writev（发送路径，非 CPU 饱和）**，不是 master（核 2 相对空闲）、不是客户端、不是环境。
  - 同机 sync（writev 到 loopback）= 2.60M，跨机 = 2.24M——差异 = 跨机 writev 路径（virtio/vhost/vSwitch 发送墙钟时延，非 softirq CPU）。ebpf 的 proxy 同理。
  - **最终定位（详见下方"跨虚拟机转发性能影响机制分析"）**：跨机 sync/ebpf 比 none 低的根因 = 跨虚拟机发送路径（writev 及其触发的 virtio/vhost/vSwitch/TCP 栈/ACK），**不是 fwd 线程单核 CPU 饱和**（实测 fwd 仅 34% CPU、`backp_stalls=0`、ss `rwnd_limited≈1%`）。
  - **为什么是"单核 per-packet"，不是"多核/算力"**：
    - 不是"多核能解决"——**复制必须保序**：单 slave 连接只能单线程顺序写（proxy fwd 线程是"唯一 writer"），多线程写同一 fd 乱序；
    - 不是"单核算力不够"——是**网络栈每包开销**（writev syscall + softirq + 收 ACK + vSwitch）在跨机比 loopback 高，单核每秒能处理的包数有限；
    - **"每包成本高"具体指什么**：发送一个包，跨机比 loopback 多付——同机 loopback 直接投递（无 vSwitch/ACK 延迟）；跨机要过 **virtio 前端/vhost 数据搬运** + **vSwitch 逐包转发（查表+复制到接收 VM）** + **接收端 NAPI/softirq** + **ACK 往返（~1ms）**（同一物理机内不经过物理网卡）。这些成本**不随包大小变化**（每包固定），吞吐 = 包数 × 每包字节，单核每秒包数有限。
    - **⚠️ 跨虚拟机转发性能影响机制分析（2026-08-30 最终定位）**：
      - **FWD_DISCARD 实验**：关闭 forward 线程的 TCP writev 发送后，跨虚拟机与同虚拟机 loopback 场景性能基本一致——二者差异由 **TCP writev 及其触发的跨虚拟机发送路径**引入，而非 master 基础命令处理或 eBPF 捕获开销；
      - **COPYFIRST 实验**（发送前复制到 forward 私有缓冲、立即推进 head 再 writev）：未带来性能恢复，**排除了慢 writev 长期引用共享 ring、延迟 head 释放作为主要原因**；
      - **steal time 均为 0**：各 vCPU 无明显的宿主调度等待（排除 vCPU 被宿主抢占）；
      - **跨虚拟机发送路径构成**：virtio 前端 → vhost/QEMU 数据搬运 → 宿主 bridge/vSwitch → 接收虚拟机 virtio → 两端 TCP 协议栈；其描述符处理、通知与唤醒、skb 管理、数据搬运及 ACK 反馈，使约 63KB 单批 writev 墙钟时间由同虚拟机的 16–32µs 增加至 64–128µs；
      - **结论：性能下降主要来自跨虚拟机发送时延和虚拟网络处理开销，而非链路峰值带宽不足**。
    - **两种转发模式的性能传导方式不同**：
      - **sync harness**：测试期间转发 ring 峰值约 12MB（< 64MB 容量），未发生 enqueue 自旋，`backp_stalls=0`；跨虚拟机发送成本主要通过**共享 LLC、内存带宽和内核 TCP/virtio 处理竞争**，表现为 reactor 的 read_avg 和 cmd_avg 上升（cmd_avg 约 287ns → 377ns）。**背压等待位于计时起点之前且 sync 未触发背压，故 +90ns 增量不代表背压等待时间**；
      - **eBPF proxy**：跨虚拟机发送同样降低 forward 服务率，积压由 **BPF ringbuf 和转发队列（queued+inflight）**共同承载；达高水位时**显式背压暂停 master 读取**，使总体吞吐收敛到跨虚拟机转发路径的持续处理能力。
    - **综上**：同虚拟机 loopback 下 sync/ebpf 可达 none 的 ~91%-98%；跨虚拟机下两者下降源于 virtio/vhost、宿主 vSwitch、两端 TCP 栈和 ACK 反馈构成的虚拟网络发送路径。**该差异不是 eBPF 机制本身的开销，也不是共享 ring 释放时机、转发线程 CPU 饱和或链路峰值带宽不足导致**。
    - **后续补充指标**：`backpressure_wait_ns / benchmark_wall_ns` 用于进一步量化 eBPF 模式背压对总耗时的贡献（现有证据已足够支持根因定位，不阻塞定稿）。
    - 缓解：① **攒批更大**（每 writev 更多命令摊薄 syscall，受 MTU 9000 包大小限制）；② 多 slave 连接/多 QP 分流（每连接内保序，架构级）；③ 减每包成本——MTU 9000（已做）、GSO/TSO（已用）、**硬件 RDMA（无 softirq，仅适用于"增量改走 RDMA"路径，见下）**。
    - **攒批实验勘误（2026-08-30）**：`FWD_BATCH_BYTES` 在当前代码中**未被 fwd 线程使用**（fwd 只按 `FWD_MAX_IOV=512` iovec 攒批、实际每批约 8 个 ring 条目 ≈ 63KB），此前"16KB→64KB 略降"的攒批实验实际测量的是 no-op；当前攒批大小由 `FWD_EMPTY_WAIT_US=200µs` 攒批窗口决定。
  - **RDMA 与 eBPF 转发的关系澄清**：当前默认 **eBPF+tcp 增量走 TCP**（优化用 MTU/GSO/TSO）；RDMA 是**另一条传输路径**——全量同步（§9）走 RDMA WRITE、legacy **kprobe+RDMA 增量**（`kvs_repl.c`）才是"增量走 RDMA"（无 softirq 是其优势）。上文"硬件 RDMA 减每包成本"是**通用网络优化清单**（若增量改走 RDMA 的理论方向），不是当前 eBPF+tcp 路径所用的。
  - 次要贡献：客户端 memtier 同机争 CPU（80-94%）+ 后台进程，但 FWD_DISCARD 证明**主因是转发线程 writev 路径**（非单核 CPU 饱和，见下）。**P=80 的 ebpf "低谷"是测量波动**（多测中位 2.25M ≈ sync）。

### 8.2 弯路：ebpf 高 P 数据丢失（2026-08-27 完整性核对）

对比 master 处理命令数与 slave tcpsink 实收数：


| ebpf 跨机 P | master 处理 | slave 实收 |        送达率 |
| ----------- | ----------: | ---------: | ------------: |
| ≤40        |          ≈ |         ≈ | ~100%（无损） |
| 80          |      13.25M |     11.03M |       **83%** |
| 160         |      14.61M |      5.23M |       **36%** |

- master 照常处理并应答全部命令（**QPS 虚高**），但 BPF 捕获只转发一部分，slave 实收远低。
- **"P=160 ebpf 比 sync 快（ebpf/sync=1.697）"是数据丢失假象，作废。**

**两个丢数据机制（一个已修、一个为架构限制）**：

1. **BPF 32KB 截断（已修复）**：捕获 BPF `CLIENT_ENTRY_MAX_LEN=32764`，对 `retval > 32764` 直接截断尾部，导致超长 recv 只转发前半。已在 `src/core/reactor.c`（生产）与 `test_ebpf_hset_qps.c`（harness）把**单次 recv 上限限制到 32KB** 修复——BPF 永远捕获完整 recv，修复后 P=80 实测 ~100% 送达（修复前 83%）。代价是读粒度变小（syscall 略增）。尝试过 BPF 内分片捕获，但 kernel 6.1 verifier 对 fexit 程序的分片循环/直排都报 `arg#0 unsupported`，故选择读侧限流。
2. **proxy 转发吞吐上限（未修复，架构性）**：跨机高 P 下 master BPF 生产（~2.8M/s）超过 proxy 的 ringbuf 排空 + 跨机转发能力，ringbuf/转发队列溢出 → BPF 丢记录（ST_RB_DROP）。sync 因 ring 满时 master 自旋天然节流故无损；ebpf 的背压（转发队列 >48MB）在 ringbuf 先满时触发不及时。顺带发现并修复了 **proxy 心跳在主线程阻塞时停止推进、导致 master 忽略背压**的隐患（改独立心跳线程）。

### 8.3 结论（诚实口径）

- **诚实（无损）的 ebpf 跨机吞吐 ≈ sync**（2026-08-28 重测 P=160 均 ~2.34M，ebpf/sync ≈ 1.0），受 master 产生 + 转发每命令成本限制；低 P（≤40）ebpf ≈ sync。
- **高 P（≥80）跨机已无损**（2026-08-28 重测 P=160 完整性 ~99.7% 送达）。旧"高 P 不可信、丢数据"结论基于 **BPF 32KB 截断（已修复）与 tcpsink 锁窗口（已修）** 的历史数据，见 §8.4。

### 8.4 ebpf 转发验证全程复盘（2026-08-28 会话全记录）

> 本会话围绕两个问题做 ebpf 验证：① **服务端什么时候回复客户端、三种复制模式的转发机制**；② **跨机 QPS 为什么低、如何定位与修复**。以下按"前置机制 → 实验（证伪→定位→修复→重测）→ 用户质疑 Q&A → 结论链 → 复现命令"完整记录。

#### 8.4.1 前置机制：回复时机、转发粒度与 v4/v6 背压

**（1）服务端什么时候回复客户端**（harness `tests/perf/test_ebpf_hset_qps.c` 的 reactor，对齐生产）：
- 回包内容：每条 HSET 解析完立即把 `+OK` 攒进该连接自己的 `out` 缓冲（`reactor_conn_read` 内循环 append，[733-735](kvstore/tests/perf/test_ebpf_hset_qps.c#L733-L735)）；
- 发送时机：**当次 `read()` 结束调用 `reactor_conn_flush` 非阻塞发**（[749](kvstore/tests/perf/test_ebpf_hset_qps.c#L749)）；EAGAIN 则注册 EPOLLOUT 下一轮续发（[504-512](kvstore/tests/perf/test_ebpf_hset_qps.c#L504-L512)）。

三种模式的回复路径差异：

| 模式 | 回复路径 | 被什么额外推迟 |
|---|---|---|
| none | `read` → 解析 → 攒 `+OK` → 当次 read 结束 flush | 无 |
| sync | 同左 + `fwd_enqueue` 转发入队（整块） | **ring 满时自旋等待**（[537-539](kvstore/tests/perf/test_ebpf_hset_qps.c#L537-L539)） |
| ebpf | `read` 前 `backpressured()` 检查 → 同左 | **proxy 落后时 usleep(100) 停"读"**（[685-688](kvstore/tests/perf/test_ebpf_hset_qps.c#L685-L688)） |

**（2）转发粒度**：一次 `read()` 收到整批 P 命令（memtier 把 P 条打包成一个大 write，P=160 × ~101B ≈ 16KB < 单次 recv 上限 32KB，所以一次 recv 能收整批）。sync 用 `batch_start` 把整批**整块入队一次**（每条仍攒一个 `+OK`）；生产 proxy 从 ringbuf **逐条出队、攒批 writev**（≤256 节点 / 512KB）。
  - **"逐条出队"** = `ringbuf_callback`（`main.c:565-601`）每条 ringbuf 记录一次回调 + 一次 `proxy_fwd_enqueue` 入队（memcpy 到稳定缓冲）。注意记录粒度 = **每次 recv**（P 大时含多条命令），所以 proxy 每命令成本随 P 摊薄；
  - **"iovec 组装"** = `proxy_fwd_thread_main`（`main.c:293-365`）从队列取节点，逐个填 `struct iovec`（`iov[niov].base/len; niov++`），攒到 `PFWD_BATCH_MAX`(256)/`PFWD_BATCH_BYTES_MAX`(512KB) 后一次 `writev`——每节点一个 iovec，也是"每个数据块一次"的操作。

**（3）v4/v6 背压机制**（ebpf 模式，`client_ctl` BPF map 三方约定，详见文档 1 §17 补充）：
- **v4** = ringbuf 背压：BPF fexit 端 `bpf_ringbuf_query` 可用数据 **≥32MB 置位**、proxy 消费端排空 **<8MB 清除**（`repl_client_capture.bpf.c:182-188`）；
- **v6** = 转发队列背压：proxy 入队 `fwdq_pending()` **>4MB 置位**、出队 **<1MB 清除**（`proxy_slave.c` 附近 `fwdq_set/clear_backpressure_locked`）；
- **心跳 v5**：proxy 每 100ms 推进，master 校验 2s 新鲜度防死锁；
- master 每次 `read()` 前查 `backpressured()`，v4/v6 任一置位则 `usleep(100)` 停手，把 ringbuf 溢出丢数据**转成 TCP 背压**（无损）。

**（4）对 QPS 的影响**：客户端是同步请求-响应模型，**回复越晚吞吐越低**。转发成本 = "转发让 master 更忙 → P=1 多连接排队延迟增大"（见 8.4.3 的 memtier 延迟实测）。

#### 8.4.2 实验：跨机 QPS 为什么低（先证伪后定位）

**起点问题**：README 跨机 sync/ebpf P=160 只有 ~1.70M/1.53M（none 3.16M，比值 ~0.53/0.48）。质疑：是不是网络限制？以下用"先证伪后定位"逐步实验。

**实验 A：链路带宽（iperf3）**——大包 10.1 Gbps，转发字节率（P=160 ~1.7M × 101B ≈ 1.37 Gbps）只占 ~10-15% → **带宽不是瓶颈**。

**实验 B：单连接"连续灌"逐层证伪**（128→129，python `sendall` / C `sendsink` 阻塞发送端；`tcpsink` select 非阻塞 / `recvsink` 阻塞接收端）：

| 发送端 | 接收端 | 连续灌吞吐 | 关键 ss 字段 |
|---|---|---|---|
| python `sendall` | tcpsink（`SO_RCVBUF=1MB`） | 1.6 G | `rwnd_limited:100%`、`rcv_ssthresh:56KB` |
| C（`SO_SNDBUF=4MB`） | recvsink（`SO_RCVBUF=4MB`） | 1.67 G | 同左 |
| C（`SO_SNDBUF=4MB`） | recvsink2（**无 SO_RCVBUF**） | 5.97 G | `rwnd_limited:0.4%` |
| C（**无 SO_SNDBUF**） | recvsink2（无 SO_RCVBUF） | **8.45 G** | — |

- **逐层证伪**：hash（`--no-hash` 一样）→ select 消费模式（阻塞 recv 一样）→ python 发送端（C 一样）→ 块大小（16KB/128KB 一样）→ 129 CPU（空闲 84-98%）→ 129 消费（纯 recv 一样）→ 发送端 `SO_SNDBUF=4MB`（去后 8.45G）。全部不是瓶颈。
- **根因：显式 `SO_RCVBUF/SO_SNDBUF` 禁用 Linux TCP 窗口 autotuning**，接收窗口锁死 ~56KB（`rcv_ssthresh`），单连接吞吐 ≈ 窗口/RTT（56KB/0.3-1ms ≈ 1.5-1.7G）。**iperf3 server 不设 SO_\*BUF**（autotuning 把窗口推到 BDP ≈ 1.1MB）故 10G。

**SO_*BUF 限制 QPS 的原理（窗口/RTT 模型）**：

- **TCP 吞吐 = min(带宽, 接收窗口/RTT, 发送窗口/RTT)**。Linux 默认开 autotuning：不设 SO_RCVBUF 时内核按实际消费动态调接收窗口（`tcp_rcv_space_adjust`），可推到 BDP（RTT×带宽）；
- **显式 `setsockopt(SO_RCVBUF)` 后内核停止 autotuning**，窗口固定 = 初始协商值（实测 `rcv_ssthresh:56588` = 56KB）；`SO_SNDBUF` 同理锁发送窗口。单连接吞吐 = 窗口/RTT（56KB/0.28ms ≈ 1.6G，实测 `rwnd_limited:100%` = 发送端一直等窗口）；
- **传导到 QPS**（转发都是单 TCP 连接）：

```
slave 端显式 SO_RCVBUF=1MB → 内核禁用接收窗口 autotuning → 窗口锁死 56KB（rcv_ssthresh）
  → 单连接吞吐 = 56KB / 窗口周转周期 ≈ 1.3-1.6 Gbps
     （周转周期 ≈ 0.28-0.34ms，由 吞吐=窗口/周期 反推，非链路 RTT 1ms）
  → 对应 ops/s = 吞吐 ÷ 每命令 101B（payload 64）≈ 1.7-2.0M ops/s
  → sync：fwd 线程 writev 被 rwnd 卡住 → ring 满 → master fwd_enqueue 自旋降速
  → ebpf：proxy writev 被 rwnd 卡住 → ringbuf/队列积压 → v4 背压 → master 停手
  实测核对：README sync P=160 = 1.70M ops/s = 1.37 Gbps，落在窗口模型内
```

- **释放（不设 SO_\*BUF）**：autotuning 把窗口推到 BDP → 单连接 8-10G → 窗口不再是瓶颈，QPS 只受 master 产生 + 转发每命令 CPU（见 8.4.3）。

**实验 C：harness 复现（memtier `-t 2 -c 50`、sync P=160）**——对端依次释放窗口：

| 对端 | QPS |
|---|---|
| tcpsink（`SO_RCVBUF=1MB`） | 1.65M（= README 1.70M，环境复现） |
| tcpsink `--no-rcvbuf` | 2.22M（**+35%**） |
| + harness fwd 去掉 `SO_SNDBUF` | 2.34M（+5%，发送端次要） |

**实验 D：修复 + 验证**：生产 `src/ebpf_proxy/proxy_slave.c` 去掉显式 `SO_SNDBUF/SO_RCVBUF`；重新编译；**`test_repl_5w5w`**（RDMA 全量 + eBPF+tcp 增量）**PASS 24/0**（预存 5w、全量 6.0s、增量 5w、追赶 8.0s、一致性 24/24）；跨机全 P 重测（§8.1 新表，高 P 比值 sync/ebpf 从 ~0.53/0.48 → ~0.74/0.74），ebpf P=160 2.34M 且**完整性核对通过**（master 捕获 3814MB vs tcpsink 实收 3824MB，~99.7% 送达；旧值丢 36%）。

#### 8.4.3 实验：P=1 转发成本（memtier 延迟 + Little's Law）

**问题**：ebpf P=1 只有 none 的 ~70%（而 sync 是 89%），为什么 ebpf 在 P=1 特别吃亏？

- **master 侧**：P=1 时 `cmds/read=1.00`（每条命令一次 recv = **每次 recv 触发一次 BPF fexit 捕获**），`cmd_avg` 1761ns vs sync 1582ns（+179ns，BPF 捕获直接内核成本）；`backp_stalls=0` 排除背压。
- **memtier 延迟实测**（P=1，`Totals` 行 `Avg. Latency`）：

| 模式 | QPS | Avg Latency | p50 | p99 |
|---|---|---|---|---|
| none | 230,490 | 0.43387ms | 0.399 | 0.951 |
| sync | 178,430 | 0.56023ms | 0.487 | 1.695 |
| ebpf | 157,820 | 0.63339ms | 0.559 | 1.487 |

- **Little's Law 映证**：P=1 时 memtier `-t 2 -c 50` = 100 连接并行，`QPS = 100/往返`，三模式 **QPS × Latency 精确 = 100**（100 连接恒有 1 个在途请求）。故 **ebpf 转发成本 = 往返 +199µs（vs none）、+73µs（vs sync）**，线性换算成 QPS 差（230k→158k）。0.633ms 是 memtier 实测（非推算）。
- **⚠️ P=1 波动大（跨轮次 ±10%）**：README 表 sync P=1 = 205,380（sweep 3 轮中位）vs 本表 178,430（另一次延迟测量），差异来自 **P=1 RTT-bound 完全暴露往返延迟**。5 次分布实测：**none 221-236k（波动 6.6%）、sync 172-176k（2.7%）、ebpf 148-163k（10.4%）**。波动来源：跨机网络 RTT 抖动（VM 共享宿主 vSwitch）+ 100 连接单线程 reactor 排队 + 后台进程抢核；**ebpf 波动最大**（叠加 BPF 捕获 + proxy 转发 + `backpressured()` 检查，master 更忙 → 排队波动放大），**sync 最小**（fwd 异步入队不阻塞 master）。**"QPS×Latency=100"用的是同一轮 memtier 输出的两个字段（轮内自洽），不跨轮次**；跨轮次对比需取多次中位并标注波动。
- **⚠️ P=1 低的主因（2026-08-30 定位）：harness `backpressured()` 无缓存，非真实服务端限制**。同机 ebpf P=1 当前实测 155k vs README 220k（用户确认真实），追查发现 **harness 未提交改动把 `backpressured()` 的 1ms 缓存去掉了**，P=1 每命令 read 前 **2 次 `bpf_map_lookup_elem`（key4+key6）syscall**，占满 master 单核（实测 87.5% CPU）→ 155k。**恢复 1ms 缓存后同机 ebpf P=1 = 212k**（vs README 220k，波动内），跨机 P=160 仍无损（master 25.51 亿 vs tcpsink 25.58 亿，~100% 送达）。**生产 `repl_ebpf_backpressure()` 有 2ms 缓存**（`kvs_repl_ebpf.c:388-391`），**不受此影响**——这是 harness 特有的测量问题。修复已提交（`test_ebpf_hset_qps.c` backpressured() 恢复缓存）。这也修正了此前"P=1 转发成本 +199µs"的一部分归因（含 harness 无缓存 bpf syscall 的假成本）。
- **结论**：cmd_avg +179ns 只占往返差 0.1%——主因是**转发让 master 更忙（BPF + proxy + softirq ≈ 43% CPU）→ P=1 多连接排队延迟增大**。这是 ebpf 在 P=1（RTT-bound、延迟敏感）吃亏的根本原因；P≥10 后一次 recv 多条命令、BPF 捕获摊薄，差距缩小。

#### 8.4.4 实验：P=80 波动与 P>40 比值降

- **P=80 ebpf "低谷"（单次 sweep 0.678）是测量波动**：该 P stddev ~133k（BPF + proxy 转发抖动大），多测中位 **2.25M**（2.14/2.25/2.36）≈ sync 2.31M（-2.5%），无真实异常低谷。
- **P>40 后 sync/ebpf 相对 none 比值下降（转发相关操作占用 CPU + 测量环境因素）**：

| P | none | sync/none | ebpf/none |
|---|---|---|---|
| 40 | 2.58M | 0.780 | 0.790 |
| 80 | 3.15M | 0.734 | 0.715 |
| 160 | 3.18M | 0.736 | 0.737 |

none 基础处理成本随 P 摊薄（P=40→80 +22%，到 master CPU 上限 3.18M）；sync/ebpf 的 master 还要做**转发相关操作**（fwd_enqueue、BPF 捕获、`backpressured()` 检查）占用 CPU，**饱和上限更低（~2.34M）**、只涨 +16%/+10% 就逼近上限 → 比值降；P=80 后三者都到各自上限、趋稳。这是预期行为（同机也如此），非异常。**再叠加测量环境**（2026-08-30 实测）：memtier 客户端与 server 同机争 4 vCPU（客户端进程 CPU 80-94%）、后台 mysqld/cpptools 占核，2.34M 部分是环境 CPU 竞争，隔离环境下真实服务端上限可能更高（详见上一条）。

#### 8.4.5 用户质疑 Q&A（会话实录）

- **Q1「同机 vs 跨机只有网络差距，网络没限制就该接近？」**：测 master(128) CPU——跨机 **softirq 7.6%** vs 同机 **1.5%**，128 idle 仍 63%（不饱和）。跨机 = 同机的 **84%**，17% 差距 = **网络处理的额外 CPU**（softirq +6%）+ RTT 交互，**非带宽**。"网络没限制"对（带宽 10G），但跨机网络处理本身吃 CPU。
- **Q2「P=1 ebpf 怎么这么低？」**：见 8.4.3——BPF 捕获每命令 + 转发让 master 更忙 → 排队延迟。
- **Q3「P=1 转发成本能确定吗？」**：能，memtier 实测 + Little's Law 映证（QPS×Latency=100），+199µs 可确定。
- **Q4「P=80 ebpf 怎么低？」**：测量波动，多测中位 2.25M ≈ sync。
- **Q5「P>40 比值都降？」**：每命令固定成本效应（见 8.4.4）。
- **Q6「0.633ms 是实际测得吗？」**：是，memtier `Totals` 行 `Avg. Latency` 实测。

#### 8.4.6 结论链

`SO_*BUF 锁窗口（主因，+42% 修正）→ 修复 proxy_slave + test_repl_5w5w 验证 → 跨机重测高 P 无损 → 剩余瓶颈 = master 产生 + 转发每命令 + 网络 softirq（非带宽）→ P=1 转发成本 +199µs（memtier 实测 + Little's Law 映证）→ 高 P 比值降 = 每命令固定成本效应`。

### Q5. 如何提高跨机 QPS（sync / ebpf）

**根因**：跨机 QPS 低，本质是**转发要走真实网络（~1ms RTT）且是小命令流**——链路带宽充裕，但**单 TCP 连接的小包/中包吞吐（per-packet 软件处理）成为上限**（2026-08-28 iperf3 实测，见下），master 的"转发 + 回复"耦合让客户端吞吐被转发拖累（客户端同步请求-响应，回复越晚 QPS 越低，见文档 1 §17 补充）。数据：跨机 sync/ebpf 只有 none 的 46-82%（README 2026-08-27 表）。提高方向分三层，按性价比排序：

**① 网络层（最直接、改动最小）**
- **MTU 9000**：跨机已验证是最大杠杆（RDMA 5.7×、sendfile 1.7×，见 §9.4）；转发走 TCP 同样受益。
- **增大 TCP 缓冲**：proxy→slave 连接发端 `SO_SNDBUF` / slave 接收端 `SO_RCVBUF`——当前 proxy 单批 512KB 就是受 slave ~1MB 发送缓冲限制（`main.c:93` 注释"≤ slave 1MB 发送缓冲，防 EAGAIN"），缓冲越大可攒的批越大。
- **更高带宽链路**（跨机物理上限）。

**② sync 模式（转发在 master 进程内，受 ring 满自旋耦合）**
- **增大 SPSC ring**（`FWD_RING_SIZE` 当前 64MB）：ring 满时 `fwd_enqueue` 自旋（`test_ebpf_hset_qps.c:537-539`），ring 越大自旋概率越低。
- **转发线程独立核 + 更大批量**：`FWD_THREAD_CPU` 已把 fwd 线程 pin 离 master 核；`FWD_MAX_IOV=512` / `FWD_BATCH_BYTES=16KB` 可调大，摊薄每命令 syscall。
- **ring 满自旋改 cond_wait 背压**：自旋是 CPU 空转（省不了 QPS，因为瓶颈在网络），改条件等待只省 CPU。
- **根本：把转发移出 master 进程**——这正是 ebpf-proxy 的架构（独立进程转发、master 只背压）。sync 想突破上限最有效的路就是向 ebpf-proxy 靠拢，或 proxy 用多连接分流（需保证复制顺序）。

**③ ebpf 模式（转发在 proxy 进程，受积压背压耦合）**
- **提高 proxy 转发吞吐**：更大批量 `PFWD_BATCH_BYTES_MAX`（512KB，受 slave 缓冲限制，先做 ① 网络层再放大）；`PFWD_BATCH_MAX=256` 节点数上限；高 P 下可考虑多转发线程/多连接（当前单 fwd 线程是唯一 writer 保证顺序）。
- **容量**：ringbuf（64MB）与转发队列（64MB）已较大，主要吸收瞬时抖动；再大收益递减。
- **水位调优**：`RB_HIGH_WATERMARK=32MB` / `PFWD_BACKPRESSURE_HIGH=4MB` 调高可延迟背压触发、让 proxy 多扛一会儿（**有 ringbuf 溢出丢数据风险**，须配合 ① 网络层让 proxy 真正变快，否则只是推迟爆雷）。
- **背压策略：从"全停"改"限速"**：当前 master 读到 v4/v6 就完全停手（`usleep(100)` 方波），对链路利用不充分；可改成按积压程度**限速 master 生产**（如逐级增大 sleep 或按比例降速），让转发链路一直满载而非"停-放"。实现更复杂，收益取决于积压占比。
- **自适应唤醒阈值**（`NO_WAKEUP`/`FORCE_WAKEUP` 8MB）微调，平衡 master CPU 与唤醒延迟。

**实测验证（2026-08-28，iperf3 跨机 128→129，MTU 9000）**——直接测"转发是不是网络限制、是哪种限制"：

| iperf3 测试（单连接） | 吞吐 |
|---|---|
| 大包默认（带宽上限） | **9.69 Gbps** |
| `-l 4096` | 7.18 Gbps |
| `-l 1024` | 3.78 Gbps |
| `-l 256` | 1.21 Gbps |
| `-l 128` | 646 Mbps |
| `-l 64` | 321 Mbps |

- **带宽不是瓶颈**：大包 9.69 Gbps，而转发字节率（P=160 1.70M ops/s × 每命令 ~53-101B ≈ **0.72-1.37 Gbps**）只占 **~8-15%**。
- **单连接吞吐 = f(包大小)，小包骤降**：64B→0.32G、128B→0.65G、256B→1.21G、4KB→7.18G。转发是几十~几百字节的命令流，正落在**吞吐快速爬升区**——跨机 QPS 被"**单 TCP 连接的小包/中包吞吐（per-packet 软件处理，vSwitch 逐包转发 + 软中断）**"卡住，**不是带宽**。
- **对优化路径的指导**：把转发字节攒成更大的段＝沿曲线向右移动、直接抬吞吐上限——这正是 proxy `PFWD_BATCH_BYTES_MAX`（受 slave ~1MB 缓冲限制）和 sync `FWD_BATCH_BYTES` 是关键杠杆的原因；MTU 9000 已有。这也是为什么"增大 TCP 缓冲 → 放大攒批"在 ① 里排最优先。

**进一步定位（2026-08-28 完整实验）：README 跨机数据主因是 `SO_RCVBUF/SO_SNDBUF` 禁用 TCP autotuning，不是小包/per-packet**

用 memtier `-t 2 -c 50`（README 同口径）复现 sync P=160 跨机，逐层释放窗口：

| 发送端 | 接收端 | QPS |
|---|---|---|
| harness fwd（`SO_SNDBUF=256KB`） | tcpsink（`SO_RCVBUF=1MB`） | **1.65M**（= README 1.70M） |
| 同左 | tcpsink `--no-rcvbuf` | **2.22M（+35%）** |
| fwd 无 `SO_SNDBUF` | tcpsink `--no-rcvbuf` | **~2.34M（+5%）** |

- **机制**：显式 `setsockopt(SO_RCVBUF)` 禁用 TCP 接收窗口 autotuning，窗口锁死 ~56KB（`rcv_ssthresh`），单连接吞吐 ≈ 窗口/RTT；`SO_SNDBUF` 同理锁发送窗口（harness fwd 256KB → ~2G，与实测 2.22M 精确吻合）。iperf3 server 不设 SO_*BUF，autotuning 把窗口推到 BDP（1ms×1.1GB/s≈1.1MB），故 10G。
- **剩余瓶颈（2.34M vs 同机 2.71M，~17%）不是带宽**：跨机网络 softirq 占 128 CPU **7.6% vs 同机 1.5%**（网络处理的额外 CPU），是"master 产生 + 转发每命令 + 网络处理 CPU"的稳态（128 idle 仍 63%，非 CPU 饱和）。
- 上面"小包骤降"（iperf3 `-l` 表）是**发送块大小效应**（单连接持续灌小块的能力），与 README 数据的瓶颈（SO_*BUF 锁窗口）是两回事；两者都靠"加大攒批/缓冲/MTU"缓解，但根因不同。

**为什么小包吞吐骤降（原理）——"每包固定处理成本"决定 pps 上限**

`吞吐 = pps × 每包字节数`。网络栈（尤其虚拟化环境）每个包有**固定处理成本**（协议栈逐包解析、vSwitch 逐帧转发、软中断/NAPI），与载荷无关。用实测反推每秒包数（payload + ~54B 头）：

| payload | 在线包 | 吞吐 | 反推 pps |
|---|---|---|---|
| 64B | 118B | 321 Mbps | ~340k |
| 128B | 182B | 646 Mbps | ~444k |
| 256B | 310B | 1.21 Gbps | ~487k |
| 1024B | 1078B | 3.78 Gbps | ~439k |
| 4096B | 4150B | 7.18 Gbps | ~216k |
| 大包 | 9000B 段 | 9.69 Gbps | ~135k |

- 64→1024B 时 pps 恒在 **~34-49 万平台**，吞吐 = pps上限 × 包大小**线性爬升**——这台 VM 的**每包处理上限 ~45 万 pps**（虚拟化 vSwitch 逐帧 + 软中断单核）。4096B 以上 pps 掉下来，才转入带宽/CPU 限制。
- **大包靠 GSO/TSO/GRO 摊薄**：发送端 GSO 一次处理大段、接收端 GRO 把同流连续段**合并成一个大 skb** 再送协议栈——协议栈只处理合并后的大包，pps 需求骤降（9.69G/9000B ≈ 13.5 万段/秒 ≪ 45 万上限）。小包时 GRO 合并条件常不满足，暴露原始逐包成本。
- **对转发的含义**：每命令几十~几百字节，若逐命令成包，1.7M ops/s 需 **170 万 pps ≫ 45 万上限** → 必须攒批把等效包变大（这正是 proxy 批量 writev 的根本价值）。
- **RDMA 同理（详见 §9）**：256KB chunk 是"**应用层消息**"不是"网络包"——在 Soft-RDMA 层被切分成 MTU 9000 的多个包，每包仍有 iWARP/RoCE 头 + 软件封装成本，同样受 per-packet 限制（单 QP ~26k 段/秒，比 TCP 还低）。所以 RDMA 提升靠 **MTU 减包数**（9000 后 5.7×）+ **RPS/并行 QP 破单核**，而不是加大 chunk。

**诚实结论（2026-08-28 修正）**：跨机 QPS 的主因 = **测试工具显式 `SO_RCVBUF/SO_SNDBUF` 禁用 TCP autotuning 锁窗口**（释放后 sync P=160 从 1.65M → 2.34M，**+42%**）；剩余瓶颈 = **master 产生 + 转发每命令 + 跨机网络处理 CPU**（softirq 7.6% vs 同机 1.5%），**不是网络带宽**（10G 只用 ~15%），也**不是"per-packet 小包"本身**（小包表是发送块大小效应）。真实 kvstore slave（reactor 不设 SO_*BUF）跨机能力应高于表值。突破方向：① **不显式设 SO_\*BUF**（保留 autotuning，收益最大）；② 增大攒批/缓冲/MTU（提升单连接窗口与段大小）；③ 提高网络处理能力。§8"ebpf 诚实吞吐不高于 sync"的结论仍成立，但两者卡住的原因需按本节修正。

## 9. 性能测试：RDMA 全量同步文件传输

> README 位置：「全量同步文件传输对比」。完整数据：`docs/data_analysis/rdma-one-sided-mtu-optimization.md`。工具：`test_rdma_throughput` / `test_sendfile_throughput` / `iperf3`，负载 85MB KVSD dump。

### 9.1 测试方法

三种传输对比：iperf3（TCP 链路上限）、sendfile（内核零拷贝）、RDMA 单边 WRITE（Soft-RDMA siw0/rxe0）。每档 3 次中位数，跨机 sha256/CMP 字节一致校验。

### 9.2 起点：初测数据有多差（2026-07）

- **跨机 RDMA 只有 iperf3 的 ~19%**：RDMA WRITE 1MB **1,020 Mbps** vs iperf3 TCP **5,370 Mbps（-81%）**；RDMA SEND 994 Mbps（-81.5%）。
- 跨机 siw0 @ MTU 1500：**0.37 Gbps**，只有 sendfile（5.1 Gbps）的 ~7%。
- 本地（同机 rxe0 loopback）可达 ~30 Gbps——**代码路径高效，瓶颈在网络**（Soft-RDMA UDP/TCP 封装 + KVM vSwitch 逐包处理）。

### 9.3 弯路：chunk 大小无关（先证伪一个方向）

chunk 256KB→8MB→81MB（整文件 1 chunk）跨机 RDMA 吞吐**恒定 ~0.41 Gbps**——**与 chunk/MR 大小无关**。瓶颈是 **per-packet 软件处理**（包数 = 数据量/MTU），包数是决定因素。**排除了"增大 chunk/MR 提升吞吐"这个错误方向。**

### 9.3b 为什么单 QP 只有 iperf3 的 ~19%（per-packet 原理，2026-08-28）

**"一次发送 85MB"是应用层视角**：85,000,008 B 在 Soft-RDMA 协议层被切成 **~2 万个 DDP/RoCE 帧**（85MB÷4096）。**关键：RDMA 协议层的帧大小不是 9000B，而是被 verbs `active_mtu` 封顶在 4096B**（MTU 9000 下 `active_mtu=4096`，见 §9.4 表）——siw（iWARP over TCP：DDP/MPA 头）/ rxe（RoCE over UDP：BTH 头）按 ≤4096B 逐帧软件封装，再经 TCP/UDP 栈 + vSwitch 逐帧转发。**帧是协议层逻辑单元，≠ 线上传输单元**：rxe 每帧 = 一个线上 UDP 包（1:1）；siw 底层是 TCP，**多个 4096B DDP 帧可合并进一个大 TCP 段**（见证据段，这解释了 siw 与 rxe 的 MTU 曲线差异）。**单 QP = 单发送队列 = 单核串行处理所有帧**，与"应用层一次写多大"无关。

**为什么不是 9.69 Gbps——两个原因叠加**：

1. **帧比 TCP 段小**：TCP 大包用 9000B 的 GSO 段（MTU 9000），RDMA 帧只有 4096B——同样数据帧数多 ~2.2 倍，每帧成本摊到更少字节；
2. **每帧软件成本更高，且没有 GRO 合并**：TCP 靠 GSO/TSO/GRO 把"每段"成本摊到大数据块（接收端 GRO 把同流段合并成一个大 skb 再送协议栈）；RDMA 每个 DDP/RoCE 帧必须被 siw/rxe **软件逐帧处理**（解析帧头、按 RKEY/MR 校验、逐帧重组写入对端 MR），**不能像 GRO 那样合并**——RDMA 语义要求逐帧。加上 siw/rxe 是内核软件实现（无硬件 offload），每帧成本 ≈ 纯 TCP 同尺寸的 **~3.6×**。

**量化对比**（同 MTU 9000）：

| 场景 | 协议层帧/段大小 | 吞吐 | 反推帧/s |
|---|---|---|---|
| **RDMA 单 QP** | 4096B（`active_mtu` 封顶） | ~1.9-2.1 Gbps | **~57-64k** |
| iperf3 TCP 大包 | 9000B GSO 段 | 9.69 Gbps | ~135k |
| iperf3 TCP `-l 4096` | 4096B | 7.18 Gbps | ~216k |

- 同 4096B 尺寸：RDMA ~60k 帧/s vs TCP ~216k 段/s → **RDMA 每帧成本 ≈ TCP 的 3.6×**；
- RDMA 帧又只有 TCP 9000B 段的 45% → 两个因素叠加，单 QP 只有 iperf3 的 ~19%。
- **单 QP 单核串行**进一步封顶——RPS + 并行 QP 破单核后 N=2 到 5.52 Gbps（见 §9.5）。

**三个证据指向"每帧处理、非 chunk/MR/数据量"**：

- chunk 无关（§9.3）：帧数 = 数据量/帧大小 不变 → 吞吐不变；
- MTU 9000 有效（§9.4）：帧从 1024→4096B（×4），帧/s 还略升（~45k→64k），吞吐 0.37→2.09（5.7×）——模型自洽。**siw 与 rxe 的 MTU 曲线差异正好验证"线上单元 vs 协议层帧"**：rxe 每 DDP 帧 = 一个线上 UDP 包（1:1），`active_mtu` 4096 封顶后线上包数不再减 → **6000→9000 平台（3.09→3.14）**；siw 底层是 TCP，**多个 4096B DDP 帧合并进一个大 TCP 段（MSS 随 MTU 增大到 ~8960）**，线上 TCP 段数继续减少、TCP 层成本（分段/软中断/vSwitch）摊薄 → **6000→9000 仍 +45%（1.44→2.09）**。所以 siw 的 MTU 优化窗口比 rxe 大：**rxe 6000 到头、siw 9000 才收敛**（且 vSwitch 封顶 9000）；
- RPS + 并行 QP 有效（§9.5）：单核串行 → 多核并行。

**为何打不过 TCP sendfile（8.79 Gbps）**：sendfile 有 **GSO/TSO/GRO 内核 offload** 摊薄每包成本（8.79G/9000B ≈ 13 万段/s）；Soft-RDMA 无等价 offload 且帧更小。除非换**真硬件 RDMA 卡**（卡上做封装与每帧处理），跨机 Soft-RDMA 追不上 TCP。

**一句话**：85MB 是应用层"一次写"，协议层是 ~2 万个 **4096B 帧**（verbs `active_mtu` 封顶，到不了 9000B）；RDMA 帧比 TCP 段小、每帧无 GRO 合并且软件成本 ≈ TCP 的 3.6×，单 QP 又单核串行 → 帧/s 只有 TCP 同尺寸的 ~1/4。**提升靠 MTU 减线上包数（rxe 受 `active_mtu` 4096 封顶、6000 到头；siw 靠 TCP 合并多帧成大段、一路受益到 9000）+ RPS/并行 QP 破单核，而非加大 chunk**——与 Q5 小包转发是同一原理（per-packet 处理决定吞吐）。

### 9.4 优化 1：MTU 1500 → 9000（2026-08-02）

**动机**：包数 = 数据量 / MTU，提高 MTU 直接打击 per-packet 瓶颈。


| 跨机 MTU |                   RDMA siw0 | RDMA rxe0 | sendfile |
| -------- | --------------------------: | --------: | -------: |
| 1500     |                   0.37 Gbps | 0.84 Gbps | 5.1 Gbps |
| 4000     |                        1.01 |      1.70 |      7.9 |
| 6000     |                        1.44 |      3.09 |      7.9 |
| **9000** |           **2.09（5.7×）** |  **3.14** |  **8.9** |
| 9216+    | 链路断（vSwitch 上限 9000） |           |          |

- siw RDMA 5.7× / rxe 3.7× / sendfile 1.7×。但即使 9000，跨机 RDMA 仍打不过 TCP sendfile（Soft-RDMA 无 GSO/TSO）。
- **弯路①：rxe0+siw0 双设备同绑 ens33 破坏跨机 RDMA**（`rdma_accept` 失败回退 TCP）——生产只建 siw0 单设备（`setup-rdma.sh`）。
- **弯路②：boot 自动创建的 rxe0 是"降级"态**（本地只有 ~9.5 Gbps vs 满血 ~30 Gbps，与 siw0 是否在场强相关）——跨机 rxe 数据是降级态下的有效测量，满血更高。
- **弯路③：MTU 9216+ 直接断链**（129 的 vNIC/vSwitch 封顶 9000），生产安全上限 = 9000。

### 9.5 优化 2：RPS + 并行 QP 破单核上限（2026-08-13）

**动机**：跨机 siw0 @MTU9000 单 QP 只有 ~1.9 Gbps（iperf3 上限的 ~19%）——**单核 siw TX 是瓶颈**。


| 配置               | 吞吐（中位） | 占 iperf3 上限 | 占 sendfile |
| ------------------ | -----------: | -------------: | ----------: |
| iperf3（链路上限） |    ~9.8 Gbps |           100% |       ~111% |
| sendfile 单 TCP    |         8.79 |           ~90% |        100% |
| RDMA 单 QP         |         1.88 |           ~19% |        ~21% |
| **RDMA N=2**       |     **5.52** |       **~56%** |    **~63%** |
| RDMA N=4           |         5.15 |           ~53% |        ~59% |

- **RPS（接收端软中断散多核）+ 并行 QP 把跨机 RDMA 从 ~19% 提到 iperf3 上限的 ~53-56%，明确超 50%**；N=2 ≈ N=4（发送端 4 vCPU 在 N=2 已饱和）。

**为什么 N=2 ≈ N=4、N=4 还略降（5.52→5.15）——并行度饱和**：

并行 QP 的实现（`tests/perf/run_rdma_parallel_qp.sh`）：**每个 QP = 一个独立进程 + 一个独立端口/TCP 连接**（siw 每连接一个 QP）——master 起 N 个 client 进程并发 WRITE（各自读文件 → siw 封装 → 提交），slave 起 N 个 server + RPS 把 ens33 单 RX 队列软中断散到所有核（`rps_cpus = (1<<nproc)-1`）。收益来源 = 把单 QP 的"**单核 per-packet 处理**"摊到多核（发送核 + RPS 接收核）。但 master/slave **都只有 4 vCPU**：

- **N=2 已基本吃满**：master 4 核要跑 2 个 client 发送进程（读文件 + siw 封装 + 提交，各占 ~1 核）+ TCP TX softirq + 脚本/监控；slave 4 核要跑 2 个 server + RPS 散的 RX softirq（siw 逐帧解析写 MR）。两端 4 核都接近饱和。
- **N=4 无新核可用，反而叠加损耗**：4 个 client 进程超订 4 vCPU → **上下文切换**；多个 QP 共享 siw 设备/PD/MR 表 → **锁竞争**；4 个 server 同时被 WRITE 写各自 MR 目标文件 → **slave 内存带宽/页缓存写回争用**；master 4 进程读同一 dump 文件 → page cache 竞争。净效果 = 不提升甚至略降。
- **对照 sendfile 多 TCP**：N=2 9.60 / N=4 9.45，同样 N=4 略降于 N=2——**多连接并行到饱和后无增益甚至略降是通用现象**（锁、缓存、调度），非 RDMA 特有。

**结论**：并行 QP 的收益上限 = **可并行的核数**（发送核 + 接收核）。4 vCPU 的 VM 上 N=2 已把两端核用满，N=4 只是增加连接数、不增加核数。要再提升需更大核数机器，或消除 siw 设备级锁竞争。
- **弯路④：sendfile 计时 bug**（`test_sendfile_throughput` 客户端 t1 在 `shutdown(SHUT_WR)` 后停表，最后一段 socket buffer 未上链路，虚高 ~3-5%）——改等对端 read EOF 再停表，客户端/服务端数字一致。
- **弯路⑤：85MB+ MR memlock**：`ibv_reg_mr` 85MB+ 报 `Cannot allocate memory`——`setrlimit(RLIMIT_MEMLOCK)` 非 root **静默失败**，且 VM 的 root 默认 memlock 也是 64MB。**必须 `sudo bash -c 'ulimit -l unlimited; ...'`**。注册/传输大小无影响（85MB→1G MR 均 ~1.88-1.92 Gbps）。
- **弯路⑥：早期"44%"是单次低值**（sendfile 定值 + 单次 RDMA 4.3），3 次中位数后修正为 ~53-56%。

### 9.6 现状

- 生产：`rdma_dev=siw0` + 两端 `ens33 mtu 9000` + RPS（`setup-rdma.sh`/service 开机持久化）。跨机 siw0 @9000 **2.09 Gbps**（MTU 优化的生产成绩）；配合 RPS+并行 QP 的独立工具实验达 **5.52 Gbps（~56% of iperf3、~63% of sendfile）**。
- 从起点 **0.37 Gbps（sendfile 的 7%）→ 2.09 Gbps（5.7×）→ 5.52 Gbps**：MTU 是配置级第一杠杆，RPS+并行 QP 是第二杠杆。
- **若只求跨机全量最快**：TCP sendfile（8.9 Gbps）仍是 Soft-RDMA 的 2.8×，且无需 RDMA 设备依赖；RDMA 的价值在绕过 TCP 全栈 + 单边（远端 CPU 不参与 recv）。

## 10. 底层共性：ECHO 热点定位（命令分派优化）

> 这条不是 README 里的独立测试，而是 **Pipeline 提速（§6 Step 5）与 AOF/Pipeline 最终数据**的底层来源——`handle_parsed_command` 的命令分派是几乎所有命令路径的公共热点。

### 10.1 perf 定位（cpu-clock, self, 稳态）


| 热点                                                           | 占比            |
| -------------------------------------------------------------- | --------------- |
| `handle_parsed_command`（strcmp 链 + 错误格式化）              | ~46%            |
| `_raw_spin_unlock_irqrestore`（kernel，conntrack/tcp softirq） | ~13%            |
| `parse_resp_stream`                                            | 9.5%            |
| `__strcmp_avx2`                                                | 5.3%            |
| `snprintf` 系                                                  | ~5%             |
| **recv / send**                                                | **0.6% / 0.5%** |

**结论：瓶颈在命令分派 + 错误格式化（合计 ~60%），不是 socket、不是 scan、不是 echo 应答本身。**

### 10.2 三个被证伪的假说（弯路）

- **memchr 解析已回退**：scan 仅 7.3%，RESP 行太短无收益。
- **on_read 拖干 256KB 已回退**：HSET P160 回退 8.4%（一次 recv 读太多反而拖慢）。
- **ECHO/PING 直写 ring 已回退**：argc=1 是死代码（echobench 必带参数）。

### 10.3 已落地优化（2026-08-25）

- **HSET/HGET/HDEL/HMOD 分派 fast path**（`goto engine_dispatch` 绕开 ~35 次 strcmp）：HSET **P=160 2.16M→3.10M（+44%）**。
- **reactor 读路径去掉冗余 EPOLLOUT 预注册**：每命令省 2 次 epoll_ctl，ECHO/HSET **+31%**。
- **repl_broadcast 无副本早退**：省 mutex+snprintf ~1.5%。
- **SET/HSET 成功应答静态字面量直写**（5 字节替换 snprintf）：HSET argc=3 真路径 **+12.6% P10 / +3% P160**。

> **验证踩坑**：`/usr/bin/perf` 在自定义内核 6.1.176 上不可用，但 `/usr/lib/linux-tools/5.15.0-139-generic/perf` 在 6.1 内核上能 record/report（此前"本机 perf 不可用"结论作废）。
